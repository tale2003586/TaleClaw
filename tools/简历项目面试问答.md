# 简历项目面试问答

> 使用方式：不要逐字背。每个问题先记住“主线答案”，再用“八股连接”补技术深度。回答时尽量控制在 60-90 秒，面试官追问时再展开。

## 一、项目总览

### 1. 请你介绍一下自研 LLM Agent Runtime 与 Coding Agent 这个项目。

**答案：**

这个项目是我从零设计的一个面向代码仓库任务的 Agent Runtime。它不是只做一次模型调用，而是把会话、模型调用、工具执行、上下文构建、记忆生命周期和 trace 记录统一纳入一个运行时框架。基于这个 Runtime，我实现了 Coding Agent，用来处理真实仓库里的代码理解、Bug 修复、功能添加、命令验证和结果总结。

我做这个项目的重点有三个：第一是让 Agent 的执行过程可控，比如工具权限、上下文预算、任务状态和失败恢复；第二是让长任务能持续推进，比如通过 checkpoint、工作记忆和 trace 支撑中断恢复；第三是让系统可评测，我构建了覆盖代码理解、修复、重构和工具调用等场景的评测流程，并接入 SWE-bench Verified 子集做自动化验证。

**八股连接：** Agent loop、状态机、工具调用、上下文工程、可观测性、评测闭环。

### 2. 这个 Runtime 和普通的大模型应用有什么区别？

**答案：**

普通大模型应用更像“输入 prompt，得到回答”，核心是一次或少数几次模型调用。而 Agent Runtime 要管理一个持续执行过程：模型需要规划、调用工具、观察结果、更新状态、继续推理，直到完成任务或失败退出。

所以 Runtime 要解决的问题更多，包括工具调用治理、上下文裁剪、任务状态持久化、多轮错误恢复、结果验证和 trace 记录。我的理解是，普通 LLM 应用更偏生成服务，Agent Runtime 更接近一个面向不确定任务的执行系统。

**八股连接：** 同步调用 vs 任务执行系统；无状态服务 vs 有状态编排；LLM inference vs Agent orchestration。

### 3. 你在这个项目里具体负责了什么？

**答案：**

这是我的自研项目，核心链路基本都是我自己设计和实现的。我主要负责 Runtime 抽象、工具调用治理、上下文管理、记忆系统、多 Agent 编排、trace 可观测链路和评测体系。

其中我投入比较多的是两个方向：一个是让 Agent 在真实仓库里能稳定执行，比如工具结果压缩、checkpoint 恢复、任务状态管理；另一个是让效果可衡量，比如上下文压缩前后的规模统计、多 Agent 编排的耗时对比、安全 RAG 的 MRR 和 Recall 指标。

**八股连接：** 系统设计、端到端工程能力、指标驱动优化。

## 二、Runtime 与工具调用治理

### 4. Runtime 抽象层主要解耦了什么？

**答案：**

我主要解耦了四类东西：第一是模型调用和业务流程，避免不同模型供应商影响 Agent 主流程；第二是工具执行和推理逻辑，模型只表达意图，Runtime 负责校验、执行和记录；第三是会话状态和执行环境，保证同一个任务可以被恢复和追踪；第四是上下文构建和推理循环，方便针对不同任务切换不同上下文策略。

这样做的好处是，后续替换模型、增加工具、调整上下文预算或接入新的评测任务，都不需要重写 Agent 主循环。

**八股连接：** 分层架构、依赖倒置、接口抽象、可扩展性。

### 5. Agent 的一次执行流程大概是什么？

**答案：**

一次执行通常是：创建任务会话，构建上下文，把系统提示、历史信息、记忆和当前请求组织给模型；模型生成下一步动作，如果是工具调用，Runtime 会做权限校验、参数校验和执行；执行结果会被记录、压缩或缓存，再进入下一轮上下文；循环直到模型给出最终答案、任务完成，或者达到失败退出条件。

结束后还会进入记忆生命周期和 trace 汇总，比如把本轮关键结果写入历史、更新近期上下文、记录模型调用和工具调用指标。

**八股连接：** ReAct、Plan-Act-Observe、状态机、事件驱动。

### 6. 工具调用治理是怎么做的？

**答案：**

我的思路是把工具分成不同风险等级和可见层级。低风险工具可以直接使用，高风险工具需要更严格的约束，比如只在特定模式下可用、需要先解锁、参数要做路径和范围校验。工具执行结果也不是无限塞回上下文，而是会做压缩、分页或缓存，避免模型因为一次大输出挤爆上下文。

这个治理的目标不是阻止 Agent 使用工具，而是让工具调用变得可控、可追踪、可恢复。尤其是代码任务里，读文件、搜索、编辑、运行命令的风险完全不同，必须分层管理。

**八股连接：** 最小权限原则、权限分层、输入校验、沙箱、审计日志。

### 7. 如何防止 Agent 滥用高风险工具？

**答案：**

主要从三层防护：第一层是工具可见性，不是所有工具默认都暴露给模型；第二层是执行前校验，比如路径必须在工作区内，参数必须符合 schema；第三层是 trace 记录，所有工具调用都会留下结构化记录，后续可以复盘为什么调用、调用了什么、结果是什么。

对于写文件、提交代码、运行命令这类高风险动作，我会尽量让它们经过更明确的执行路径，而不是让模型在任何时候随意调用。

**八股连接：** 白名单、schema 校验、路径穿越防护、审计追踪。

### 8. 工具调用失败后怎么处理？

**答案：**

我会区分失败类型。如果是参数错误或路径错误，这类通常把错误结果反馈给模型，让模型重新规划；如果是临时性错误，比如命令超时或外部服务抖动，可以考虑有限重试；如果是高风险写操作失败，就不能盲目重试，需要保证不会造成重复修改。

所以核心原则是：读操作可以更积极地重试，写操作要考虑幂等性和副作用，必要时让模型重新分析当前状态。

**八股连接：** 异常分类、幂等性、重试退避、补偿机制。

### 9. Checkpoint 里应该保存哪些内容？

**答案：**

Checkpoint 不是简单保存一段对话，而是要保存恢复任务所需的关键状态。我的设计里会关注任务状态、工具执行结果、上下文压缩结果、工作区变更信息和当前推理进度。

这样恢复时，系统能知道哪些步骤已经完成、哪些工具结果可以复用、当前上下文应该从哪里继续构建。否则长任务一旦中断，就只能重新读文件、重新搜索、重新推理，既浪费时间，也容易产生重复操作。

**八股连接：** 状态持久化、断点续跑、任务恢复、Exactly-once / At-least-once 语义。

### 10. 如何避免恢复后重复执行已经完成的工具调用？

**答案：**

核心是把工具调用结果和任务进度结构化记录下来，而不是只依赖模型记忆。恢复时先读取已有状态，如果某一步工具结果仍然有效，就直接复用或引用；如果涉及工作区变化，则要检查当前文件状态和记录中的状态是否一致。

对于有副作用的操作，不能简单按“上次失败了再来一次”处理，要通过状态记录判断是否已经部分完成。

**八股连接：** 幂等设计、去重键、状态机、写操作副作用。

## 三、多 Agent 编排

### 11. 多 Agent 编排为什么能降低耗时？

**答案：**

复杂代码任务通常不是一个线性问题，很多子问题可以并行探索，比如不同目录的代码结构、不同模块的调用关系、不同失败原因的定位。我的设计会按任务分解和文件边界派发子任务，让子 Agent 在隔离上下文中做局部探索，再把结果汇总给主 Agent。

这样可以减少主 Agent 反复全仓搜索和重复阅读文件的成本，也能降低单个上下文里塞入太多无关信息的问题。简历里写的平均执行耗时降低 55%，就是在复杂任务场景下和不启用编排的 baseline 做对比得到的。

**八股连接：** 并行化、任务拆分、上下文隔离、A/B 对比。

### 12. 任务是按什么粒度拆分给子 Agent 的？

**答案：**

我倾向于按文件边界、模块边界和问题类型拆分。比如一个任务涉及路由、工具执行和上下文压缩，就可以让不同子任务分别定位相关模块和关键逻辑。这样每个子 Agent 的上下文更小，目标更明确，返回结果也更容易被主 Agent 合并。

我不会让子 Agent 处理过大的开放式任务，因为那样会导致它们重复搜索、结论不可控，反而增加汇总成本。

**八股连接：** 分治、任务粒度、并发调度、上下文窗口。

### 13. 多 Agent 会不会造成上下文竞争？

**答案：**

会，所以我做了上下文隔离。每个子 Agent 只拿到自己的任务描述、有限的范围提示和必要的工具，不共享完整主上下文。它们返回的是结构化结论，比如覆盖了哪些文件、发现了什么、还有哪些不确定点。

这样主 Agent 汇总时看到的是压缩后的证据，而不是多个子 Agent 的完整推理历史，可以减少上下文污染和重复信息。

**八股连接：** 隔离性、信息压缩、map-reduce 思路、并发任务汇总。

### 14. 如果多个 Agent 修改同一个文件怎么办？

**答案：**

我的设计更偏保守：子 Agent 更适合做定位、提取和分析，真正的写操作尽量由主 Agent 汇总后执行。这样可以避免多个 Agent 同时改同一个文件造成冲突。

如果要支持并发写，就需要引入更严格的冲突检测，比如记录每个任务的文件范围、修改前版本、diff 合并结果，并在提交前检查是否存在重叠修改。

**八股连接：** 并发控制、乐观锁、冲突检测、diff 合并。

## 四、上下文工程

### 15. 你说的双模式上下文管理是什么？

**答案：**

我把上下文分成通用模式和代码模式。通用模式适合普通对话和轻量任务，会把记忆、历史、当前请求、工具结果等按 Section 组织，每个 Section 有独立预算和压缩规则。

代码模式更关注任务执行状态，不是简单保留聊天历史，而是把工具结果、子任务返回、压缩事件和中断事件组织成结构化任务状态。这样在长代码任务中，模型更容易知道“当前做到哪了、哪些结论可靠、下一步该干什么”。

**八股连接：** 上下文窗口、Section budget、状态压缩、任务状态机。

### 16. 为什么不能简单截断上下文？

**答案：**

简单截断最大的问题是可能把关键约束、工具结果或当前任务目标截掉，导致模型出现重复工作或错误决策。我的做法是按信息类型分预算：当前请求和关键任务状态优先保留，历史内容、长工具输出和低优先级上下文可以压缩或引用式保留。

所以压缩的目标不是让文本变短，而是在有限窗口里保留决策所需的信息。

**八股连接：** 信息优先级、摘要压缩、head-tail 保留、上下文污染。

### 17. 61.2k 降到 43.8k 后怎么证明效果没有明显下降？

**答案：**

不能只看上下文变短，还要看任务是否完成、工具调用是否变少、失败率是否变化，以及关键评测集上的表现。我会把压缩前后的上下文规模、任务完成情况、模型调用次数、工具调用次数和失败原因都记录到 trace 中，再做对比。

如果压缩后上下文变短但失败率上升，说明压缩策略伤害了关键信息，需要调整不同 Section 的预算和保留规则。

**八股连接：** 消融实验、指标对比、质量-成本 trade-off。

### 18. 工具结果很长时怎么处理？

**答案：**

我不会把完整工具结果直接塞回模型上下文。通常会做几件事：结果分页，只返回必要窗口；长结果压缩，保留摘要和关键行；结果缓存，让后续需要时可以重新取；对于代码文件，先看结构或搜索结果，再按行读取目标片段。

这样可以降低 token 消耗，也能减少模型被大量无关输出干扰。

**八股连接：** 分页、缓存、懒加载、大对象引用、上下文预算。

## 五、分层记忆系统

### 19. 你的记忆系统分哪几层？

**答案：**

我把记忆分为短期工作记忆、长期稳定记忆、候选记忆和冷记忆召回。短期工作记忆服务当前任务，记录任务进展、已完成事项和待处理问题；长期稳定记忆保存用户偏好、项目约定这类长期有效信息；候选记忆用于暂存可能有价值但还不确定的信息；冷记忆召回则通过向量检索从历史会话中找相关旧 turn。

这套分层的核心是：不同生命周期的信息不要混在一起，否则会导致记忆污染、上下文膨胀和跨任务误召回。

**八股连接：** 缓存分层、冷热数据、生命周期管理、数据治理。

### 20. 为什么候选记忆不能直接写入长期记忆？

**答案：**

因为用户的一句话不一定代表稳定偏好，也可能只是一次临时需求。如果直接写入长期记忆，后面很容易误导模型。我的做法是先进入候选区，再结合历史相似证据、触发次数和置信度判断是否晋升。

晋升后也不是简单保存原话，而是提炼成更稳定、更可复用的记忆表达。

**八股连接：** 噪声过滤、置信度、证据累计、数据质量。

### 21. 记忆召回如何避免串用户、串任务？

**答案：**

我在召回时会做作用域隔离。历史向量记录不仅有文本向量，也带有 scope 信息，查询时先限定用户或任务边界，再做相似度召回。这样不同用户、不同会话或不同任务的历史不会混在一起。

这点在 Agent 系统里很重要，因为记忆一旦串了，不只是回答不准确，还可能带来隐私和安全问题。

**八股连接：** 多租户隔离、权限边界、metadata filter、隐私安全。

### 22. 召回到错误记忆怎么办？

**答案：**

我会从三个方向降低影响。第一是设置召回阈值和 top-k，避免低相关内容进入上下文；第二是把召回结果作为辅助上下文，而不是覆盖当前请求；第三是保留 trace，记录召回了哪些历史、分数是多少、最终注入了什么，方便定位问题。

如果某类任务经常误召回，就需要优化 embedding、过滤条件或上下文注入策略。

**八股连接：** 召回精度、阈值控制、可解释性、trace debug。

## 六、可观测性与失败分析

### 23. trace 系统记录哪些内容？

**答案：**

我主要记录上下文构建、模型调用、工具调用、token 消耗、耗时、压缩状态和失败原因。对于 RAG 任务，还会记录检索决策、命中证据和最终注入内容。

这样一次任务失败后，我可以沿着 trace 看：是不是上下文构建时丢了关键信息，是不是模型选错了工具，是不是工具调用失败，还是检索召回或排序出了问题。

**八股连接：** 可观测性、结构化日志、链路追踪、指标监控。

### 24. 任务失败后如何定位问题？

**答案：**

我会先看失败发生在哪一层：模型输出层、工具执行层、上下文层、检索层还是评测验证层。然后看对应 trace，比如模型是否拿到了足够上下文、工具参数是否正确、工具结果是否被压缩过度、RAG 是否召回了正确证据。

这比只看最终回答有效，因为 Agent 任务往往是多步链路，一个最终错误可能来自中间任意一步。

**八股连接：** 分层排障、错误归因、日志关联、根因分析。

## 七、安全 RAG 系统

### 25. 你的安全 RAG 和普通文档 RAG 有什么区别？

**答案：**

普通文档 RAG 更关注语义相关，而安全 RAG 还必须关注证据可靠性、元数据过滤和安全场景匹配。比如一个漏洞知识片段不仅要有文本，还要保留 CVE、CWE、严重等级、语言、影响组件等元数据，这样才能在代码审查场景中做细粒度过滤和证据追踪。

另外安全 RAG 的回答不能只像知识问答，还要服务于漏洞定位和修复建议，所以要能把代码片段、危险 API、漏洞模式和外部安全知识关联起来。

**八股连接：** 领域 RAG、metadata filtering、证据可追溯、幻觉控制。

### 26. 安全知识建模是怎么做的？

**答案：**

我把不同来源和格式的安全资料统一成结构化知识模型。原始数据可能来自 Markdown、HTML、JSON 等格式，处理时会做解析、清洗、切分，并提取安全相关元数据，比如 CVE、CWE、Severity、Language 等。

这样后续检索时既可以做语义召回，也可以基于结构化字段做过滤和排序，最终回答还能追踪到证据来源。

**八股连接：** ETL、schema 设计、数据清洗、结构化索引。

### 27. chunk 切分怎么设计？

**答案：**

安全知识不能只按固定长度硬切，因为一个漏洞描述、影响范围、利用条件和修复建议经常是一个整体。如果切得太碎，召回后缺上下文；切得太大，又会影响检索精度和注入成本。

我的思路是结合文档结构和内容语义切分，尽量让一个 chunk 保留完整安全事实，同时保留元数据，便于后续过滤和证据追踪。

**八股连接：** chunk size、overlap、语义完整性、召回率与精度。

### 28. Hybrid Search 里 dense 和 sparse 分别解决什么？

**答案：**

Dense 向量检索擅长语义相似，比如用户没有说出完全相同的漏洞名，但表达了相似风险；Sparse 检索擅长精确匹配，比如 CVE 编号、CWE 编号、函数名、库名、危险 API 这类关键词。

安全场景里两者都重要，因为有些问题靠语义，有些问题必须精确命中特定编号或组件。Hybrid Search 可以兼顾这两类需求。

**八股连接：** 向量检索、BM25/稀疏检索、语义匹配、关键词匹配。

### 29. RRF 为什么适合做多路召回融合？

**答案：**

不同召回方式的分数分布不一样，dense 的相似度、sparse 的打分和其他召回分数不能直接相加。RRF 更关注排名位置，而不是原始分数，所以可以更稳定地融合多路结果。

它的好处是简单、鲁棒，不需要为每种检索方式手动做复杂归一化，适合多阶段检索链路里的候选融合。

**八股连接：** Rank fusion、分数归一化、排序稳定性、多路召回。

### 30. Reranker 放在什么位置？为什么需要它？

**答案：**

Reranker 放在召回之后、最终注入上下文之前。召回阶段要追求覆盖面，所以会拿到一批候选；Reranker 再从候选里判断哪些和当前问题最相关。

只靠向量召回容易出现“语义上像但证据不够精确”的情况，尤其安全问题经常涉及具体漏洞类型、组件版本和修复建议，所以需要精排来提升最终证据质量。

**八股连接：** bi-encoder vs cross-encoder、召回与精排、Top-K rerank。

### 31. 选择性 rewrite 是什么？为什么不是每次都 rewrite？

**答案：**

选择性 rewrite 是只在查询表达不完整、缺少检索关键词或需要补全安全语义时才改写问题。不是每次都 rewrite，因为改写可能引入意图漂移，把用户原本的问题改偏，尤其安全场景里一个词变了，可能对应完全不同的漏洞类型。

所以 rewrite 的目标是增强召回，而不是替代用户原始意图。

**八股连接：** 查询改写、意图保持、召回增强、意图漂移。

### 32. “先召回、后决策”的证据驱动路由是什么意思？

**答案：**

传统做法可能先判断这个问题要不要走 RAG，再决定是否检索。但这样如果分类器误判，就会直接错过知识库证据。我的思路是先做轻量召回，看看有没有足够强的证据，再决定是否注入 RAG 内容。

这样可以减少“本来应该用知识库但被路由拒绝”的情况。在召回效果基本不变的情况下，我通过优化链路把 P50 延迟降低了约 25%。

**八股连接：** 路由策略、误拒风险、召回成本、延迟优化。

### 33. P50 延迟降低 25% 是怎么来的？

**答案：**

这个指标是对检索链路做前后对比得到的，关注中位数延迟。优化方向主要包括减少不必要的 LLM rewrite 或分类调用、调整路由顺序、让检索决策更多依赖已有证据，而不是每次都走完整重链路。

我不会只看延迟，还会同时看 MRR 和 Recall，确保不是通过少检索、少召回牺牲效果换来的速度。

**八股连接：** P50/P95、性能 profiling、延迟-效果权衡、消融实验。

## 八、代码感知检索

### 34. 如何从代码中提取安全相关信息？

**答案：**

我会从代码里提取几类信号：依赖组件、危险 API、输入输出路径、认证鉴权逻辑、文件上传、命令执行、反序列化等安全敏感模式。这些信号可以来自静态规则、文本搜索、代码结构分析，也可以结合模型做语义判断。

提取后再和安全知识库里的 CVE、CWE、漏洞模式和修复建议做联合召回。

**八股连接：** 静态分析、AST、规则引擎、污点分析基础。

### 35. 如何避免安全 RAG 误报？

**答案：**

我会强调证据链，而不是只看相似度。比如代码里出现危险 API，不代表一定有漏洞，还要看输入是否可控、是否经过校验、依赖版本是否受影响、是否有上下文约束。

所以最终建议里要区分“确认风险”“疑似风险”和“需要更多上下文验证”，并尽量引用命中的证据来源。

**八股连接：** 误报/漏报、证据链、数据流、上下文敏感分析。

### 36. 修复建议如何避免模型编造？

**答案：**

修复建议必须绑定检索证据。我的做法是把命中的安全知识、对应元数据和注入内容都记录到 trace，同时在回答时围绕证据给出建议。如果证据不足，就不能强行下结论，而是说明需要补充版本、调用链或配置上下文。

这样可以降低幻觉，也方便事后判断问题来自召回、排序还是生成。

**八股连接：** grounded generation、引用证据、幻觉控制、可追溯性。

## 九、评测与指标

### 37. MRR 和 Recall@10 分别说明什么？

**答案：**

MRR 关注正确答案排得有多靠前，如果第一个结果就是正确证据，MRR 就高；Recall@10 关注前 10 个结果里有没有召回正确证据，衡量覆盖能力。

两个都要看。Recall 高说明没有漏掉证据，但如果 MRR 低，说明正确证据排得靠后，最终注入上下文时可能还是用不到。

**八股连接：** 信息检索指标、排序质量、召回覆盖。

### 38. 250 条评测集怎么构造才合理？

**答案：**

评测集需要覆盖真实用户会问的问题，也要有模型自问的问题、困难样本和反例。比如安全知识问答、漏洞定位、修复建议、CVE/CWE 查询、非安全问题、不可回答问题都应该覆盖。

同时要避免只用一种表达方式，否则模型和检索系统会对固定问法过拟合。评测时还要记录每条问题期望命中的证据，才能计算 MRR 和 Recall。

**八股连接：** 测试集设计、数据偏差、负样本、标注标准。

### 39. 如果 Recall 很高但回答很差，可能是什么原因？

**答案：**

可能有几类原因。第一，正确证据虽然召回了，但排序靠后，没有进入最终上下文；第二，注入的上下文太长，模型没有抓住关键证据；第三，生成阶段没有严格基于证据回答；第四，问题本身需要代码上下文，但只召回了通用知识。

所以排查时要分层看召回、排序、注入和生成，而不是只看最终答案。

**八股连接：** RAG 链路拆解、错误归因、检索-生成脱节。

### 40. 怎么判断问题来自召回、排序还是路由？

**答案：**

我会看 trace。首先看路由是否决定走 RAG；如果没走，但问题需要知识库，就是路由问题。其次看候选里有没有正确证据；如果没有，是召回问题。如果候选里有但排得很靠后，是排序或 rerank 问题。如果正确证据已经注入，但回答仍然错，就是生成或 prompt 约束问题。

这种分层归因对优化 RAG 很重要，否则只看最终回答无法定位瓶颈。

**八股连接：** observability、链路分解、ablation、debug trace。

## 十、工程化与后端基础

### 41. 如果向量库挂了，系统怎么降级？

**答案：**

向量库挂了不应该让整个 Agent 系统不可用。可以降级为不做语义历史召回，只使用当前会话、长期本地记忆和普通工具检索；同时记录错误和降级状态，避免静默失败。

对于安全 RAG，如果知识库不可用，就应该明确说明无法提供可溯源安全证据，而不是让模型凭空回答。

**八股连接：** 降级、熔断、可用性、故障隔离。

### 42. 为什么不同数据不都放在一个存储里？

**答案：**

因为不同数据访问模式不同。结构化任务状态、用户信息、trace 元数据适合关系型数据库；完整历史 turn 的语义召回适合向量库；长期稳定记忆适合可审计、可编辑的本地文档或结构化文件。

把所有数据强行塞到一个存储里，会让查询、审计、召回和维护都变复杂。

**八股连接：** 存储选型、OLTP、向量检索、冷热分层。

### 43. FastAPI 或后端服务里，长任务应该怎么处理？

**答案：**

长任务不适合同步阻塞请求。更好的方式是请求进来后创建任务，后台执行，前端或调用方通过任务状态查询进度。任务执行中要记录状态、trace 和失败原因，必要时支持重试或恢复。

Agent 任务尤其适合这种模式，因为它可能包含多轮模型调用、工具调用和验证步骤，耗时不可控。

**八股连接：** 异步任务、后台队列、任务状态、超时控制。

### 44. Docker 部署时你会关注什么？

**答案：**

我会关注服务依赖、环境变量、数据卷、健康检查和日志。比如向量库、数据库、应用服务之间要有清晰的启动和连接配置；持久化数据不能只放容器内部；健康检查要能发现服务不可用；日志要方便排查模型调用、检索和工具执行问题。

**八股连接：** 容器化、服务编排、持久化、健康检查。

## 十一、高压追问速记

### 45. 你这个项目最难的点是什么？

**答案：**

最难的是让 Agent 从“能跑 demo”变成“能在真实仓库里稳定执行”。真实任务里上下文会膨胀，工具结果会很长，模型会选错工具，长任务会中断，检索也可能召回错误证据。所以我把重点放在工具治理、上下文预算、checkpoint、trace 和评测闭环上。

这个项目对我的提升也在这里：我不只是调 prompt，而是在做一个可控、可观测、可恢复的 Agent 执行系统。

**八股连接：** 工程化、系统稳定性、复杂系统治理。

### 46. 如果让你继续优化，你会做什么？

**答案：**

我会继续做三件事。第一，引入更强的代码结构理解能力，让 repo map、代码检索和代码修改更精准；第二，完善多 Agent 写操作冲突检测，让并行不只用于分析，也能更安全地参与修改；第三，扩展评测集和线上 trace 分析，把失败样本自动归因到上下文、工具、检索或模型本身。

**八股连接：** AST/tree-sitter、并发控制、自动化评测、持续优化。

### 47. 你怎么证明这不是简单套壳？

**答案：**

简单套壳通常只是在模型外面包几个工具调用，而我的项目重点在 Runtime 能力：有任务会话、工具权限、上下文预算、记忆生命周期、checkpoint、trace、评测和 RAG 证据链。这些都是让 Agent 在真实任务中可控执行的基础设施。

另外我也不是只展示效果，而是记录了上下文规模、耗时、检索指标和失败原因，用工程指标证明系统优化。

**八股连接：** 基础设施能力、可观测性、评测指标、工程闭环。

### 48. 你项目里最能体现工程能力的一点是什么？

**答案：**

我觉得是把不确定的 Agent 行为拆成可治理的工程链路。比如模型输出不确定，就用工具 schema、权限和执行校验约束；上下文不确定，就做分层预算和压缩；任务长且容易失败，就做 checkpoint 和 trace；检索质量不稳定，就做评测集和指标拆解。

也就是说，我不是只追求模型一次答对，而是让系统在失败时能定位、能恢复、能继续优化。

**八股连接：** 系统设计、鲁棒性、可维护性、可观测性。
