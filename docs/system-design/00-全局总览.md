# 全局架构导览：从一条消息到一次可追踪的 Agent Run

这篇文档把当前项目讲成一条完整系统链路。

读完以后应该能回答这些问题：

- 这个项目现在是什么，不是什么
- 一条用户消息从入口进来以后怎么被处理
- bot 聊天和 coding task 为什么是两条不同执行路径
- 模型、工具、记忆、插件、trace 分别在什么位置
- 当前有哪些状态会落盘，哪些能力还没有实现

## 项目现在是什么

当前项目是一个多入口 agent runtime。它不是单纯的 CLI coding harness，也不是只有一个模型请求函数的聊天壳。

它已经具备这些核心能力：

- 多入口消息抽象：CLI、Web、Telegram、飞书等入口最终都会转成统一的 inbound/outbound message。
- 会话管理：每个 chat/session 有自己的消息历史、模式、metadata 和用户身份。
- 模式路由：普通聊天、coding、hybrid 路由会决定本轮走哪个 profile 和工具模式。
- 推理循环：模型调用、工具调用、工具结果回填、停止条件由 `ReasoningLoop` 推进。
- 工具治理：工具注册、按模式可见、延迟解锁、hook 拒绝、循环保护和 trace 记录。
- 受限文件区：bot/coding 都可以使用按用户隔离的 storage、临时 sandbox 和 artifact 发布工具，但这些不是通用 workspace 写权限。
- coding task session：coding 请求会被隔离到任务 session，可以绑定真实 workspace 并记录 diff。
- working memory：coding route 会把断点式任务状态存入 session metadata，支持用户停止后通过“继续”/`resume` 注入已完成与待办线索。
- 记忆生命周期：会话后处理会生成 history、recent context、pending memory，并支持按用户隔离；默认会放到后台线程执行，避免阻塞用户回复。
- 记忆召回与历史向量索引：长期记忆仍以本地 Markdown 和关系型存储为主，Qdrant 可作为历史 turn 和 memory 文件的召回索引。
- 代码安全 RAG：可把本地代码安全知识库切片后写入 Qdrant，支持自动上下文注入和 `security_rag_search` 工具检索。
- 运行证据：每次 run 会写 `run_state.json`、`trace.jsonl`、`metrics.json`、`report.json`。
- trace 索引：本地 run 工件仍是主证据，同时把 run/step 摘要索引到 PostgreSQL；未配置 DSN 时索引初始化会失败。
- 插件机制：插件可以加工具、hook、turn 拦截、run report、eval report；默认装配 shell safety、status、web search、安全 RAG、Markdown PDF 和 run report 插件。
- benchmark：coding benchmark 可以跑 scripted 或真实模型，并输出 `summary.json`、`rows.json` 和插件生成的 `summary.md`。

## 项目现在不是什么

为了避免误读，当前项目还不是这些东西：

- 不是完整的分布式调度平台。后台任务、team bus、短生命周期 subagent 已存在，但主 runtime 仍以单进程本地执行为主。
- 不是完整 workflow checkpoint/replay 系统。现在有 working memory、session、run artifact 和 workspace diff，能做断点式续做提示，但不能从某个 exact reasoning step 或 tool call 重放。
- 不是全仓代码索引 RAG。当前 RAG 主要面向代码安全知识库和历史会话召回，不是对任意工作仓库做完整语义索引。
- 不是强审批工作流。工具有 hook 和模式边界，但没有完整的人类审批队列。

## 三条主线

可以把当前系统压成三条主线。

| 主线 | 作用 | 关键模块 |
| --- | --- | --- |
| 控制面 | 决定一条消息怎么被路由、执行和停止 | `runtime/bootstrap.py`、`runtime/agent_loop.py`、`runtime/pipeline.py`、`runtime/reasoning_loop.py` |
| 能力面 | 决定模型能看见什么、能调用什么、能写哪里 | `models/`、`tools/`、`runtime/context.py`、`runtime/workspace.py`、`plugins/`、`knowledge/`、`retrieval/` |
| 证据面 | 决定系统怎么被复盘、测试和比较 | `runtime/trace/`、`.runs/`、`evaluation/`、`benchmarks/`、`plugins/run_report`、`plugins/eval_report`、`knowledge/tracing.py` |

## 一条消息的大致路径

一条用户消息进入系统后，会走下面这条线：

1. 外部入口把消息转成 `InboundMessage`，写入 `MessageBus`。
2. `AppRuntime.start()` 启动 outbound dispatch，入口侧可以持续收发消息。
3. `AgentLoop.run_once()` 从 bus 取出 inbound。
4. `SessionManager` 根据 `inbound.session_key` 获取或创建 session。
5. `AgentLoop` 校验 inbound metadata 里的用户身份，并创建 `RunState`。
6. `PluginManager.before_turn()` 有机会提前拦截，比如状态命令。
7. `ModeRouter` 根据 session 和用户文本选择 route/profile。
8. 如果是 coding profile，进入 `TaskSessionRunner.run_coding_task()`。
9. 如果不是 coding profile，进入 `Pipeline.run()`。
10. `Pipeline` 重置 turn 状态、标记本轮安全 RAG 自动注入尚未使用，并把上下文构建交给 `ContextBuilder`。
11. `ContextBuilder` 组装 system prompt、instructions、history、active turn、working memory、相关记忆、历史召回、安全 RAG 和 task runtime events。
12. `ReasoningLoop` 循环执行模型调用、工具调用和工具结果回填，并在每次调用前做 context sanitize 和 token gate。
13. 本轮完成后，`Pipeline` 触发记忆生命周期；默认通过 `BackgroundMemoryLifecycle.enqueue_after_turn()` 调度后台任务，非后台模式才同步调用 `MemoryLifecycle.after_turn()`。
14. `AgentLoop` 写 run 状态、trace/report/metrics/trace summary，并触发 `plugins/run_report`。
15. 回复通过 `MessageBus.publish_outbound()` 发回对应 channel/chat。

## Runtime 装配点

当前主要装配入口是 `runtime/bootstrap.py` 的 `build_runtime()`。

这个函数负责把这些对象组装成一个 `AppRuntime`：

- `MessageBus`
- `SessionManager`
- `TraceStore`
- `ToolRegistry`
- 懒初始化的 `ModelPool` 和 routed provider
- `ModeRouter`
- `ScopedMemoryStore`
- `MemoryLifecycle`
- 可选包装后的 `BackgroundMemoryLifecycle`
- history vector index、memory processor、security RAG router/index
- `PluginManager`，以及默认插件 `ShellSafetyPlugin`、`StatusCommandsPlugin`、`WebSearchPlugin`、`SecurityRagPlugin`、`MarkdownPdfPlugin`、`RunReportPlugin`
- `ToolExecutor`
- `ReflectionAgent`
- `Pipeline`
- `TaskSessionRunner`
- `TaskSubagentRunner`
- `AgentLoop`

这也是理解系统依赖关系的最好入口。大部分核心对象不是在使用时临时创建，而是在启动时装配好，再通过 `AgentLoop` 串起来。

## 普通聊天和 Coding 的区别

普通聊天路径直接使用主 session：

- 用户消息追加到当前 session。
- `Pipeline.run()` 构建上下文并进入 reasoning loop。
- 工具按 profile 的 `tool_mode` 暴露。
- 结束后调度或更新同一个 session 的记忆生命周期，并按当前请求召回相关记忆，而不是默认整包注入所有 memory 文件。

coding 路径会额外创建 task session：

- 父 session 只记录用户请求和最终摘要。
- `TaskSessionFactory` 创建隔离任务 session，并把 task 状态写入父 run 的 `metadata.task_session`。
- `WorkspaceResolver` 解析并绑定真实 workspace。
- task session 使用 task-local memory。
- working memory 从父 session 继承到 task session，结束后再同步回父 session。
- 任务完成后做结论抽取和可晋升记忆筛选。
- 如果有 trace，会记录 workspace before/after snapshot 和 diff。

这个设计把长期聊天和一次代码任务分开，避免 coding 中间步骤污染主会话。

## 运行证据在哪里

单个 run 的证据默认在：

```text
.runs/<run_id>/
```

里面主要包括：

- `run_state.json`：本次 run 的状态快照。
- `trace.jsonl`：按时间追加的结构化事件。
- `metrics.json`：从 trace 聚合出来的模型、工具、token、耗时指标。
- `report.json`：机器可读的 run 报告。
- `trace_summary.json` / `trace_summary.md`：从 trace、metrics、report 聚合出的执行路径、失败分类、workspace、工具和记忆处理摘要。
- `report.md`：由 `plugins/run_report` 生成的人类可读报告。
- `workspace_diff.json`：coding task 绑定 workspace 且启用 trace 时生成。

如果 `TRACE_INDEX_ENABLED` 未关闭，`TraceStore` 还会把 run 和 execution path step 索引进 `TraceIndexStore`。连接通常通过 `TRACE_DATABASE_URL` 或 `DATABASE_URL` 指定；没有这些环境变量时不会创建本地关系型索引文件，而是直接暴露配置错误。

benchmark 的证据默认在：

```text
.evals/runs/<eval_id>/
```

里面包括：

- `summary.json`
- `rows.json`
- `summary.md`，由 `plugins/eval_report` 生成
- `runs/<run_id>/`，每条 benchmark task 的 run 证据
- `sessions/` 和 `memory/`，benchmark 隔离运行时状态

## 当前设计最重要的取舍

第一，系统以消息和 session 为边界，而不是以 CLI 调用为中心。这让 Web、Telegram、飞书和 CLI 可以共享 runtime。

第二，coding 不是普通聊天里打开几个写文件工具，而是进入 task session。这给 workspace、memory、diff、artifact 留出了隔离点。

第三，工具不是直接从模型输出执行。模型只能请求工具，工具是否可见、能不能执行、参数是否会被 hook 改写或拒绝，都由工具层统一处理。coding 模式现在预加载核心读写、git、task/subagent 工具；更高风险或协作类工具仍可保持 deferred。

第四，trace 是运行时的一等产物。模型调用、工具调用、context sanitize、token emergency trim、workspace diff、memory lifecycle 和 RAG 检索都会落结构化事件或独立 JSONL，不只靠最终回答判断系统行为。

第五，记忆生命周期默认不在用户回复路径上阻塞。主 run 可以先完成并出站，后台记忆任务随后继续补写 `memory.lifecycle.*` 事件并刷新 trace summary。

第六，working memory 是 session metadata 中的任务状态，不是独立调度系统。它适合记录“已完成/待继续/最近停止原因”，帮助下一轮 coding 上下文续做；但真正的执行流仍由新一轮 `ReasoningLoop` 重新推进。

## 当前边界

现在已经能做 run 级 trace 和 benchmark，但还有一些边界要清楚：

- working memory 已支持断点式续做提示，但没有 step 级 checkpoint replay、持久任务队列或自动工作流恢复判定。
- 没有全仓代码索引上下文。
- prompt 预算治理已经有 section budget、conversation summary、active turn 压缩和 token gate，但不是完整的 provider 级 prompt cache / checkpoint 方案。
- 工具审批更多是 hook/policy，不是人类审批流。
- 后台记忆是本地线程池里的 best-effort 后处理，不是持久任务队列；进程退出前若没有等待任务完成，仍可能丢失尚未完成的派生记忆更新。
- OpenTelemetry 还没有直接导出，只是 trace 事件结构已经具备 span/request/session/run/tool_call 等字段，并有关系型索引辅助查询。

## 总结

当前项目的核心不是“模型加工具”，而是一套围绕消息、会话、路由、工具边界、coding task、trace 和 benchmark 组织起来的 runtime。

它最有价值的部分在于：每次执行都有边界，每个工具调用有治理，每个 coding task 有 workspace diff，每次 benchmark 有可复盘的 rows 和 summary。后续要往工业级继续走，重点应该放在 step 级 checkpoint/replay、审批流、OpenTelemetry 导出和更强的上下文索引上。
