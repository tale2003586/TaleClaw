# 工具接入、可见性与执行护栏

这篇文档讲模型为什么不能直接执行外部动作，以及当前工具层怎么控制可见性、执行和审计。

## 这层解决什么问题

对 agent runtime 来说，危险的地方不在模型会说什么，而在模型能不能随便做什么。

当前项目把工具调用拆成几层：

- `tools/schema.py` 定义工具 schema。
- `tools/handlers.py` 提供具体 handler。
- `ToolRegistry` 注册工具、控制模式可见性和延迟解锁。
- `ToolPolicy` 决定某个 turn 能看见和执行哪些工具。
- `ToolExecutor` 统一执行 hook 链、记录耗时和错误。
- `tools/hooks.py` 提供文件写边界、循环保护、trace hook 等护栏。
- 插件可以注册额外工具和 hook。

模型只能请求工具。工具是否可见、能否执行、参数是否被改写、是否被拒绝，都由 runtime 决定。

## ToolRegistry 做什么

`ToolRegistry` 维护工具表：

```python
self._tools: dict[str, ToolSpec]
```

每个 `ToolSpec` 包含：

- name
- schema
- handler
- risk
- enabled_modes
- source
- always_on
- session_scoped
- admin_only

注册入口是：

```python
registry.register(schema, handler, risk=..., enabled_modes=...)
```

主工具注册由 `build_lead_tool_registry()` 完成。

## 工具模式

工具会按模式启用。当前常见模式包括：

- `bot`
- `coding`
- `teammate`

例如 coding 工具包含：

- `list_files`
- `rg`
- `grep`
- `nl`
- `read_file`
- `write_file`
- `edit_file`
- `bash`
- `git_status`
- `git_diff`
- `git_log`
- `git_branch`
- `git_add`
- `git_commit`
- `load_skill`
- task board 工具，例如 `task_create`、`task_update`、`task_list`、`task_get`、`claim_task`
- task/team/background 相关工具
- memory 工具
- storage / sandbox / artifact 工具，通常在 coding 中按需解锁

bot 模式则更偏向这些安全范围工具：

- `load_skill`
- `recall_memory` / `memorize`
- `storage_list_files` / `storage_read_file` / `storage_write_file`
- `sandbox_list_files` / `sandbox_read_file` / `sandbox_write_file`
- `publish_artifact`
- 插件提供的 `runtime_status`、`web_search`、`markdown_to_pdf`

## 可见性和延迟解锁

工具不一定每轮都全部暴露给模型。

`schemas_for_turn(session, mode)` 会通过：

```python
visible_names = self.visible_names_for_turn(session, mode)
```

拿到本 turn 可见工具，再把这些工具 schema 交给模型。

如果工具是 deferred，模型需要先调用 `tool_search`：

```text
tool_search(query="...")
tool_search(query="select:<tool_name>")
```

选择后工具名会写入 session metadata 的 unlock 列表，下一轮 reasoning step 才能看见。

这个设计可以减少模型一开始看到的工具噪声，也能降低高风险工具被随意调用的概率。

为了减少模型乱猜工具名，runtime 还会在每次模型调用的上下文里追加一个轻量 `<tool_catalog>`：

- `Visible now`：本 step 可以直接调用的工具名和一句描述。
- `Available after unlock`：当前 mode 允许、但需要 `tool_search(query="select:<tool_name>")` 后才能调用的工具。

这个目录只告诉模型“有哪些工具名可用”，不会绕过 schema 可见性。模型真正能调用的工具仍然由 `schemas_for_turn(session, mode)` 决定。

如果模型需要查某个工具的参数格式，可以调用：

```text
tool_search(query="help:<tool_name>")
tool_search(query="schema:<tool_name>")
```

如果工具不存在，或者当前 mode 不允许，`tool_search` 会直接返回 `Unknown tool` / `not allowed`，避免模型在无效工具名上反复试探。

当前 coding 模式会直接预加载核心工作工具：

- `list_files`
- `read_file`
- `write_file`
- `edit_file`
- `bash`
- `git_status`
- `git_diff`
- `git_log`
- `git_branch`
- `load_skill`
- `task_create`
- `task_update`
- `task_list`
- `task_get`
- `task`
- `parallel_tasks`
- `claim_task`
- `check_background`
- `read_inbox`
- `compact`

这样 coding agent 不需要先花一步 `tool_search` 才能改文件或跑测试。更有副作用或低频的工具仍然保持 deferred，例如：

- `git_add`
- `git_commit`
- `background_run`
- storage / sandbox / artifact 工具在 coding 模式允许使用，但默认不预加载，需要时通过 `tool_search` 解锁
- teammate / broadcast / shutdown 类工具

bot 模式仍然看不到通用 `bash`、`write_file`、`edit_file`，只能使用 storage / sandbox 这类受限工具。

插件也可以注册工具。例如 `plugins/security_rag/plugin.py` 注册了 `security_rag_search`，在 bot 和 coding 模式可用，但不是 always-on；模型可以通过 `tool_search` 解锁后手动查询本地代码安全知识库。

## 默认插件集

`runtime/bootstrap.py` 当前默认装配这些插件：

- `ShellSafetyPlugin`：提供 shell 命令危险模式和 workspace cd 边界 hook。
- `StatusCommandsPlugin`：注册 `runtime_status` 工具，并在 `before_turn` 直接拦截 `/status`、`/plugins`。
- `WebSearchPlugin`：注册 always-on 的 `web_search` 工具，支持 general/news/finance 查询。
- `SecurityRagPlugin`：注册 deferred 的 `security_rag_search` 工具。
- `MarkdownPdfPlugin`：注册 always-on 的 `markdown_to_pdf` 工具。
- `RunReportPlugin`：在 `after_run` 阶段写 `report.md`。

benchmark 侧还会装配 `EvalReportPlugin`，用于在 eval 结束后写 `summary.md`。

插件注册的工具和本地工具走同一套 `ToolRegistry`、`ToolPolicy`、`ToolExecutor` 和 trace 边界。

## skill 工具

本地技能由 `skill_runtime/loader.py` 在启动时扫描：

```text
skills/**/SKILL.md
```

`SkillLoader.get_descriptions()` 只提供技能名、description 和 tags，用于轻量暴露能力目录。真正的技能正文不会默认塞进上下文，需要模型调用：

```text
load_skill(name="...")
```

`load_skill` 会返回 `<skill name="...">...</skill>`。这个设计和 deferred tools 类似：先给模型知道“有哪些技能”，需要时再取完整内容，避免系统 prompt 被所有技能正文撑大。

## storage、sandbox 和 artifact 工具

storage / sandbox 工具不是通用文件系统写权限。

storage root 由 `user_scope.storage_root_for_session()` 决定：

```text
.users/<user_id>/storage/
```

没有显式 `user_id` 的旧本地 session 会回退到：

```text
storage/
```

storage 工具的边界是：

- `storage_list_files` / `storage_read_file` 只能访问当前用户 storage root 下的非隐藏路径。
- `storage_write_file` 只允许创建 `storage/generated/` 下的文本类 artifact，且不会覆盖已有文件。
- 写入会追加 `records/storage_writes.jsonl`，记录路径、字节数和 sha256。

sandbox root 是临时草稿区：

```text
.task_sandbox/sessions/<session_hash>/
.task_sandbox/tasks/<task_id>/
```

sandbox 工具的边界是：

- 路径不能绝对、不能包含 `..`、不能进入隐藏路径。
- `sandbox_write_file` 默认不覆盖已有文件，除非显式 `overwrite=true`。
- `publish_artifact` 会把 sandbox 里的完成品复制到当前用户 `storage/generated/`，并记录 artifact 元数据。
- `cleanup_expired_sandboxes()` 会按 `TASK_SANDBOX_TTL_HOURS` 清理过期 sandbox。

Web、Telegram 和飞书的文件列表、预览、下载命令也使用同一套用户 storage 边界。

## web_search 预算

`WebSearchPlugin` 把 `web_search` 注册为 bot/coding 下 always-on 的低风险工具，但 `ReasoningLoop` 仍会做 turn 级预算。

每轮 `Pipeline._before_turn()` 默认设置：

```text
web_search_budget_limit = 6
web_search_budget_used = 0
web_search_budget_remaining = 6
```

每次执行 `web_search` 都会扣减额度，并把 `<web-search-budget ...>` 片段加到工具结果前面，提醒模型剩余次数。额度耗尽时，不再调用插件 handler，而是直接返回 `status="denied"` 风格的工具结果，要求模型基于已有检索结果完成回答。

## session_scoped 工具

一些工具必须知道当前 session，例如：

- workspace 文件工具
- git 工具
- memory 工具
- sandbox/storage 工具

这些工具在执行时会被注入 `_session`：

```python
if tool.session_scoped or name in SESSION_SCOPED_TOOLS:
    handler_args["_session"] = session
```

这样 handler 可以从 session metadata 里拿到：

- user id
- workspace root
- task session 信息
- storage scope

## ToolExecutor 做什么

`ToolExecutor.execute()` 是所有工具真正执行前后的统一边界。

它做这些事：

1. 复制原始 arguments。
2. 依次执行 pre hooks。
3. 如果 hook 改写参数，就使用改写后的参数。
4. 如果 hook 拒绝，就返回 `status="denied"`。
5. 调用 invoker 执行真实 handler。
6. 捕获异常，返回 `status="error"`。
7. 执行 after hooks。
8. 返回 `ToolExecutionResult`。

结果里会保留：

- `status`
- `output`
- `final_arguments`
- `duration_ms`
- `error_type`
- `error_message`
- `pre_hook_trace`
- `post_hook_trace`

这些字段会进入 session tool message 和 trace。

## 当前已有的关键 hook

`runtime/bootstrap.py` 里装配了：

- `FileWriteScopeHook()`
- `ToolLoopGuardHook()`
- `ToolTraceHook()`
- 插件提供的 hooks

其中默认插件还包括 `ShellSafetyPlugin()`，它会注册：

- `ShellSafetyHook`
- `ShellWorkspaceScopeHook`

因此 shell 工具实际会同时受命令危险模式和 workspace cd 边界约束。

benchmark 里也会按 workspace 装配：

```python
ToolExecutor([
    FileWriteScopeHook(workspace),
    ToolLoopGuardHook(),
    ToolTraceHook(),
])
```

这说明文件写边界不是只靠模型提示词约束，而是实际执行前的 hook 约束。

`ToolLoopGuardHook` 现在有两层保护：

- 完全相同的 `tool + arguments` 指纹重复达到阈值会拒绝。
- 同一个工具名在窗口内过于频繁使用也会拒绝。

每个 turn 开始时，`AgentRunner.reset_turn_state()` 会调用 executor 的 `reset_turn(session.id)`，避免上一轮的工具历史污染下一轮。

## workspace 文件工具的边界

真实 workspace 由 `runtime/workspace.py` 管：

- `WorkspaceResolver` 解析 workspace。
- `allowed_roots` 限制可用根目录。
- `safe_workspace_path()` 拒绝绝对路径和 `..` 逃逸。

文件工具会从 session metadata 读取 `workspace_root`，并确保路径不逃出这个 root。

## git 工具

当前系统已经有 git 相关工具：

- `git_status`
- `git_diff`
- `git_log`
- `git_branch`
- `git_add`
- `git_commit`

这些工具同样是 workspace/session scoped，并受工具可见性和高风险策略约束。

其中 `git_add`、`git_commit` 被标为高风险工具。

## 短生命周期 subagent 工具

coding 模式现在直接预加载：

- `task`
- `parallel_tasks`

它们不是持久 teammate 进程，而是通过 `agents/subagent/runner.py` 的 `TaskSubagentRunner` 创建短生命周期子 session，并复用主 pipeline 的模型、工具 executor 和 reflection 配置。

子 agent 的能力由 `agents/subagent/tools.py` 控制：

- `explore`：只读探索为主。
- `plan`：读取上下文并产出计划。
- `code`：允许 focused edits 和验证。

`TaskSubagentRunner` 会为子任务创建隔离 `Session`，复制父 session 的 workspace metadata，并使用新的 `ContextBuilder(memory_store=None, security_auto_context_enabled=False)`。这意味着子 agent 默认不继承主会话记忆，也不会自动注入安全 RAG；如果它需要安全知识，可以通过允许的 `security_rag_search` 工具手动检索。

`parallel_tasks` 会并发运行多个短生命周期子任务，并把每个子任务的 summary、files_touched、tool_count、error 汇总回主 agent。

在 dispatch 前，handler 会校验子任务 scope，要求 `scope.files` 是已验证的具体 workspace-relative 文件，且数量不超过配置限制。dispatch 和 result 还会写入 working memory checkpoint：已派发任务进入 pending，完成或失败结果会更新 completed/pending 和 failure reason。

## team bus 结构化消息

持久 teammate / lead 通信使用 `bus/protocol.py` 的 `AgentMessage`：

- `sender`
- `recipient`
- `type`
- `payload`
- `id`
- `correlation_id`
- `ttl_seconds`

`render_agent_message()` 会把结构化消息渲染成模型可读的 `<agent_message ...>`。`bus/reliable.py` 的 `ReliableMessageBus` 提供 request/response correlation，但当前主执行路径更常用的是 `send_message`、`read_inbox`、`broadcast` 这些工具。

## 工具调用如何进入 trace

`ReasoningLoop._execute_tool_calls()` 会为每个 tool call 写：

- `tool.call.started`
- `tool.call.completed`
- `tool.call.failed`
- 兼容事件 `tool_executed`

payload 会包含：

- `tool_call_id`
- `tool_name`
- `status`
- `duration_ms`
- `execution_error`
- 入参摘要
- 出参摘要
- hook trace

所以工具不是黑盒执行。失败原因、拒绝原因、最终参数都能从 trace 里看到。

## 当前边界

当前工具层还没有完整人类审批队列。

它已有的是：

- 模式可见性。
- deferred unlock。
- admin-only。
- workspace path guard。
- hook deny。
- tool loop guard。
- trace 记录。
- 短生命周期 subagent 的工具白名单。
- team bus 的结构化消息协议。

如果后续要加强，可以在 `ToolExecutor` 的 pre-hook 层加 approval hook，把某些高风险操作挂起，等待人类确认后再继续。

## 总结

当前工具设计的核心是：模型只能提出工具调用意图，runtime 才能决定工具是否可见、是否允许、最终参数是什么、执行结果如何记录。

这层让 trace、benchmark 和 workspace diff 都变得可信，因为所有外部动作都会经过同一个执行边界。
