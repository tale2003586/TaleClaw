# 运行时主循环与执行编排

这篇文档讲一条用户消息进入 runtime 后，怎么被推进成一次完整 run。

## 这层解决什么问题

用户只发一句话，但系统要做很多事：

- 找到 session。
- 建立 run 状态。
- 调插件。
- 路由到 bot 或 coding。
- 构建上下文。
- 调模型。
- 执行工具。
- 写 trace 和报告。
- 更新记忆。
- 发出回复。

这些动作的编排中心是 `runtime/agent_loop.py`。

更底层的模型-工具循环在 `runtime/reasoning_loop.py`。

## AgentLoop.run_once()

`AgentLoop.run_once()` 是一轮 inbound 的主入口。

它按顺序做这些事：

1. 从 `MessageBus` 取出 inbound。
2. 根据 `inbound.session_key` 获取或创建 session。
3. 应用 inbound 身份。
4. 创建 `RunState` 并写入 trace。
5. 执行 `plugin_manager.before_turn()`。
6. 用 `ModeRouter` 选择 route。
7. 把用户消息写入 session。
8. 如果是 coding profile 且 working memory checkpoint 开启，准备本轮 working memory。
9. 根据 route 决定走 coding task session 还是普通 pipeline。
10. 执行 `plugin_manager.after_turn()`。
11. 完成 run，写 run state/report/trace。
12. 保存 session。
13. 发布 outbound 回复。

如果中间抛异常，会走 `_fail_run()`，把 run 标记为 failed 并写错误。

有一个顺序边界需要注意：`plugin_manager.before_turn()` 发生在用户消息写入 session 之前。如果插件返回 `abort=True`，例如 `/status` 或 `/plugins` 被 `StatusCommandsPlugin` 拦截，本轮会形成 `execution_path="plugin_abort"` 的 run，直接写报告并发送回复，但不会把这条用户命令追加进普通对话历史。

## RunState 的作用

`RunState` 是一次执行的状态对象。

创建时会记录：

- `run_id`
- `session_id`
- `channel`
- `chat_id`
- `user_id`
- `user_role`
- 当前 mode
- execution path
- started time
- metadata

运行中会更新：

- route 结果
- reasoning steps
- tool calls
- last tool
- stop reason
- final answer
- error
- finished time

`AgentLoop._start_run()` 会把 `active_run_id` 和 `last_run_id` 写到 session metadata。这让 session 能知道当前正在跑哪个 run。

## 路由之后的两条路径

路由结果由 `ModeRouter.route()` 给出，里面包含：

- intent
- execution
- profile
- tool_mode
- confidence
- reason
- switched

如果 `route.switched` 为 true，说明这轮只是切换模式。系统会直接回复切换消息，不进入模型推理。

如果 profile 的 `tool_mode == "coding"`，进入：

```python
self.task_session_runner.run_coding_task(...)
```

否则进入：

```python
self.pipeline.run(...)
```

## Pipeline 的职责

`Pipeline` 当前主要负责 turn 级编排：

- turn 前 reset 工具状态，包括工具解锁状态和 tool loop guard 状态。
- turn 前初始化 turn-scoped 运行状态，包括安全 RAG 自动注入标记和 `web_search` 每轮预算。
- 记录本轮 active turn 起点，也就是最新 user message 的 index。
- 每个 reasoning step 前构建 context，并把 active turn 起点传给 `ContextBuilder`。
- 限制安全 RAG 自动上下文每个用户 turn 只注入一次。
- 在 active turn 前插入 `<tool_catalog>`，告诉模型本 step 哪些工具可见、哪些 deferred 工具可解锁。
- 决定模型 purpose：coding profile 用 `coding`，否则用 `chat`。
- reasoning loop 结束后触发 memory lifecycle；默认是入队后台线程，关闭后台模式时才同步执行。

`Pipeline` 不直接执行模型工具循环。它把这部分交给 `AgentRunner` 和 `ReasoningLoop`。

## ReasoningLoop 的职责

`ReasoningLoop.run()` 是模型-工具循环。

每一轮 reasoning step 会做：

1. 检查用户是否请求取消。
2. 检查是否超过 `max_reasoning_steps`。
3. 记录 reasoning step 到 run state。
4. trace `reasoning.step.started`。
5. 调 `build_context(session, profile)` 构建模型 messages。
6. trace context build start/completed。
7. 对 context messages 做 provider 前 sanitize。
8. 用 `runtime/token_estimator.py` 估算 token，如果超过 provider 安全阈值，执行 `emergency_trim()`。
9. 调 provider 的 `chat` 或 `stream_chat`。
10. 把模型返回的 assistant message 写回 session。
11. 如果没有 tool calls，本轮结束，并把 coding working memory 标记为 completed。
12. 如果有 tool calls，逐个执行工具。
13. 把 tool result 写回 session。
14. 根据 loop guard、不可用工具、reflection 决定继续或停止。

这是一条标准的：

```text
context -> model -> assistant/tool_calls -> tool results -> context -> model
```

闭环。

## 停止条件

当前主要停止条件有：

- 模型返回无 tool call 的 assistant final message。
- 用户主动停止当前 turn。
- reasoning steps 超过上限。
- 工具循环保护触发。
- 模型重复请求当前不可用工具。
- reflection agent 要求 stop。
- provider 或工具执行异常导致 run failed。
- 模型连续两次返回空回复且没有工具调用。

停止时如果是正常 final，会调用 `after_turn(session)`；如果是保护性停止或用户取消，会写一条 assistant guard/partial message，然后同样调用 `after_turn(session)`。

coding profile 下如果 `WORKING_MEMORY_CHECKPOINT_ENABLED` 开启，保护性停止和用户取消会调用 `checkpoint_turn_stopped()`，把 working memory 标记为 `suspended` 并记录停止原因。正常 final 会调用 `complete_working_memory()`，把状态标记为 `completed`。

## 后台记忆调度

`Pipeline._after_turn()` 会检查 memory lifecycle 是否提供 `enqueue_after_turn()`。

默认 `runtime/bootstrap.py` 在 `MEMORY_LIFECYCLE_BACKGROUND=1` 时会把 `MemoryLifecycle` 包成：

```python
BackgroundMemoryLifecycle(memory_lifecycle)
```

这时主回复不会等待 history summary、candidate memory、向量索引、recent context 归档全部完成。后台任务会拿 session 的 deepcopy 快照执行，避免后续 session 继续变化时影响本次记忆处理。

相关 trace 事件包括：

- `memory.lifecycle.scheduled`
- 后台任务内部转写的 `memory.*` 事件
- `memory.lifecycle.completed`
- `memory.lifecycle.failed`

后台任务完成后会尝试刷新 `trace_summary`，所以某个 run 的初始报告可能先出现，随后补上 memory 处理摘要。

## Trace 如何嵌入主循环

主循环不是跑完才补 trace。关键节点会立即写事件：

- `run.started`
- `inbound_received`
- `route_selected`
- `reasoning.step.started`
- `context.build.started`
- `context.build.completed`
- `context.sanitized`
- `context_emergency_trim`
- `model.call.started`
- `model.call.completed`
- `model.call.failed`
- `model.route.attempts`
- `tool.call.started`
- `tool.call.completed`
- `tool.call.failed`
- `memory.lifecycle.scheduled`
- `memory.lifecycle.completed`
- `memory.lifecycle.failed`
- `run_finished`
- `run.failed`

这些事件会进入 `.runs/<run_id>/trace.jsonl`。

## 当前边界

运行时主循环已经有清晰 run 边界、trace、用户取消和 working memory 续做提示，但还没有这些能力：

- run 中断后从某个 exact reasoning step 或 tool call 重放。
- 持久化工作队列。
- 多 worker 并发调度。
- 人类审批后继续执行。

当前系统更准确的定位是：单进程、多入口、有状态、可追踪的 agent runtime。它已有短生命周期 subagent 和 team bus 协作能力，但这些仍运行在同一主进程和本地工具边界内。

## 总结

`AgentLoop` 决定一条 inbound 怎么变成一次 run。`Pipeline` 决定一个 turn 怎么准备上下文、标记 active turn、注入工具目录和更新记忆。`ReasoningLoop` 决定模型和工具如何循环，并在 provider 调用前执行 sanitize 与 token gate。

三者分工合起来，构成了当前项目的主执行链。
