# 数据持久化、索引与本地工件边界

这篇文档讲当前系统里哪些数据进入关系型数据库，哪些保留为本地文件工件，哪些进入 Qdrant。

## 这层解决什么问题

项目现在不是单一存储架构。

不同数据有不同生命周期：

- 会话消息需要恢复和查询。
- run trace 需要保留原始证据。
- trace index 需要给 UI 快速筛选。
- memory Markdown 需要人工可读、可编辑。
- 完整历史 turn 需要向量召回。
- 代码安全知识库需要独立 RAG collection。

因此当前设计是：

- PostgreSQL 负责状态、索引、用户、会话和可查询记录。
- Qdrant 负责语义召回。
- 本地文件负责原始证据、人工可读记忆和评测工件。

核心实现位于：

- `runtime/db.py`
- `user_scope.py`
- `sessions/session_store.py`
- `web/auth_store.py`
- `memory/scoped_store.py`
- `memory/archive_store.py`
- `memory/candidates.py`
- `memory/vector_runtime.py`
- `memory/qdrant_index.py`
- `runtime/trace/trace_store.py`
- `runtime/trace/index_store.py`
- `knowledge/security_rag.py`

## runtime/db.py

`runtime/db.py` 是应用层的数据库连接适配入口。

它提供：

- `DatabaseConfig`
- `resolve_database_config()`
- `connect()`
- `execute_many()`
- `sql()`
- `row_get()`
- `is_integrity_error()`

推荐生产路径使用 PostgreSQL：

```text
DATABASE_URL=postgresql://...
```

各个 store 也可以通过更具体的环境变量覆盖，例如：

- `SESSION_DATABASE_URL`
- `TRACE_DATABASE_URL`
- `WEB_AUTH_DATABASE_URL`
- `MEMORY_ARCHIVE_DATABASE_URL`

实际解析顺序是：

1. 调用方显式传入的 PostgreSQL DSN。
2. 专用环境变量。
3. `DATABASE_URL`。

值必须以 `postgres://` 或 `postgresql://` 开头；否则会直接报错，避免隐式创建本地关系型数据库文件。

## 会话存储

会话存储实现位于：

```text
sessions/session_store.py
```

它存两张逻辑表：

- `sessions`
- `messages`

推荐配置：

```text
SESSION_DATABASE_URL=postgresql://...
```

如果没有配置 `SESSION_DATABASE_URL`，会尝试复用：

```text
DATABASE_URL
```

如果两者都没有配置，`SessionStore` 会直接报错。

`SessionStore.save_session()` 是增量写入：它会读取已有 `seq/message_json`，找到第一条变化的消息，然后删除并重写变化后的尾部。这样不会每次都重写整段历史。`last_message_insert_count` 记录本次实际插入的消息行数，主要用于测试和观测。

## Web Auth 存储

Web 用户和认证信息由：

```text
web/auth_store.py
```

管理。

它同样通过 `runtime/db.py` 连接关系型数据库。解析顺序是：

```text
WEB_AUTH_DATABASE_URL -> DATABASE_URL
```

Web auth 存两类数据：

- `web_users`：user id、PBKDF2 password hash、salt、role、source。
- `web_auth_sessions`：浏览器 opaque token 的 sha256 hash、user id、过期时间。

配置不匹配时，常见报错是：

```text
password authentication failed for user "agent"
```

这不是应用 schema 错误，而是 Postgres 用户、密码、数据库或 `DATABASE_URL` 配置不匹配。

## 本地 Markdown 记忆

稳定记忆仍然是本地 Markdown 文件，不迁移到 Qdrant 或 PostgreSQL 作为唯一真相源。

带有 `user_id` 的 session 会通过 `ScopedMemoryStore` 使用：

```text
.users/<user_id>/memory/
```

没有显式用户身份的旧本地 session 会回退到：

```text
memory/
```

典型文件包括：

- `SELF.md`
- `MEMORY.md`
- `NOW.md`
- `HISTORY.md`
- `RECENT_CONTEXT.md`
- `PENDING.json`

原因是：

- 人可以直接打开检查。
- 适合手工修正。
- 适合在 prompt 中以文本形式注入。
- 不依赖数据库服务才能被人阅读。

Qdrant 只负责历史 turn 和 memory files 的向量召回，不替代这些 Markdown 文件。

## 用户 Storage

用户文件区由 `user_scope.storage_root_for_session()` 和 `storage_root_for_user()` 解析：

```text
.users/<user_id>/storage/
```

没有显式用户身份时回退到：

```text
storage/
```

这里存放：

- Web 上传文件。
- bot/coding storage 工具生成的 artifact。
- sandbox 发布后的成品。
- `records/storage_writes.jsonl` 等 artifact 记录。

storage 是用户私有文件区，不是 coding workspace。coding workspace 仍由 `WorkspaceResolver` 和 `workspace_root` metadata 绑定。

## 候选记忆存储

候选记忆由：

```text
memory/candidates.py
```

管理。

当前实现把候选记忆存成 `PENDING.json`。文件中记录：

- candidate id。
- 用户描述。
- normalized key。
- trigger count。
- confidence。
- evidence。
- promoted 状态。

`PENDING.json` 同时也是人工可读镜像。镜像里会写 `backend: "json"`。

候选记忆支持：

- upsert。
- 相似候选触发。
- trigger count 累计。
- confidence 更新。
- promoted 标记。

满足条件后，`MemoryLifecycle` 会调用 LLM 提取稳定记忆，并写回本地 Markdown 记忆。

## Memory Archive

recent context 被挤出后，会进入 archive store。

实现位于：

```text
memory/archive_store.py
```

推荐配置：

```text
MEMORY_ARCHIVE_DATABASE_URL=postgresql://...
```

如果没有单独配置，会尝试复用 `DATABASE_URL`。

如果没有 `MEMORY_ARCHIVE_DATABASE_URL`、`SESSION_DATABASE_URL` 或 `DATABASE_URL`，初始化会直接报错。当前 `runtime/db.py` 已经移除了本地 SQLite/path fallback，关系型存储必须使用 PostgreSQL DSN。

## 历史会话向量库

历史会话向量库由：

```text
memory/vector_runtime.py
memory/qdrant_index.py
```

管理。

开启方式：

```text
HISTORY_VECTOR_ENABLED=1
HISTORY_VECTOR_BACKEND=qdrant
QDRANT_COLLECTION=taleclaw_history
```

它存的是完整历史 turn，包括：

- user message
- assistant message
- tool calls
- tool result

scope 通常是：

- `user:<user_id>`
- `task:<task_id>`

注意：历史会话向量库不是 memory Markdown 的替代品。它服务的是“从过去完整对话中召回相关 turn”。

## 代码安全 RAG collection

代码安全 RAG 使用另一套 Qdrant collection：

```text
SECURITY_RAG_COLLECTION=code_security_kb_bge_m3
```

它存的是外部安全知识库切片，不存用户会话。

这两套 collection 必须分开：

- 历史会话：用户私有上下文。
- 安全知识库：项目级或全局知识源。

混在一起会带来权限、召回噪音和生命周期问题。

## Run Trace 文件

run 原始证据由 `runtime/trace/trace_store.py` 写到：

```text
.runs/<run_id>/
```

主要文件：

- `run_state.json`
- `trace.jsonl`
- `report.json`
- `metrics.json`
- `trace_summary.json`
- `trace_summary.md`
- `report.md`

这些文件是 run 的事实来源。即使关系型索引失败，也应该保留这些工件。

## Trace 关系型索引

trace index 由：

```text
runtime/trace/index_store.py
```

维护。

推荐配置：

```text
TRACE_INDEX_ENABLED=1
TRACE_DATABASE_URL=postgresql://...
```

如果没有配置 `TRACE_DATABASE_URL`，会尝试复用 `DATABASE_URL`。

如果两者都没有配置，`TraceIndexStore` 会直接报错。

`TRACE_INDEX_ENABLED` 默认开启，显式设置为 `0`、`false`、`no` 或 `off` 才会关闭。

索引用于：

- run 列表。
- run 状态筛选。
- 按 session / user / 时间查询。
- execution path 快速展示。
- Web UI 避免每次扫 `.runs` 下所有 JSONL。

索引不是完整 trace warehouse，也不替代 `.runs` 原始文件。

## 本地 transcript

Web 或调试路径下可能会生成 transcript 文件，例如：

```text
.transcripts/*.jsonl
```

这类文件是会话调试材料，不应该被模型主动当作恢复上下文的工具来源。正常上下文恢复应该走 session store、memory store、trace summary 或明确的用户请求。

## 推荐边界

当前推荐边界是：

| 数据 | 推荐存储 |
| --- | --- |
| session / messages | PostgreSQL |
| working memory | session metadata，随 session 存入 PostgreSQL |
| auth / users | PostgreSQL |
| stable memory | `.users/<user_id>/memory/` 下的本地 Markdown |
| user storage / artifacts | `.users/<user_id>/storage/` |
| candidate memory | `PENDING.json` |
| memory archive | PostgreSQL |
| history vector | Qdrant |
| security RAG | Qdrant 独立 collection |
| raw run trace | `.runs/<run_id>` 本地文件 |
| trace index | PostgreSQL |
| eval artifacts | `.evals/` 本地文件 |

## 当前边界

当前持久化系统已经按关系型数据库、Qdrant、本地工件三层组织，但仍有边界：

- 原始 trace 还没有集中式对象存储。
- PostgreSQL 仍依赖各 store 初始化 schema，不是集中式 schema migration 工具。
- Qdrant collection schema 变更需要新 collection 或重建 ingest。
- 本地 Markdown 记忆仍是稳定记忆的主要形态，不适合直接删掉。
- `.evals/` 和 `.runs/` 仍是评测与调试证据的重要来源。

## 总结

当前系统不是“所有东西塞进一个数据库”，而是按数据用途分层：

关系型数据库负责状态和索引，Qdrant 负责语义召回，本地文件负责原始证据和人工可读记忆。这个边界能兼顾开发可调试性、UI 查询效率和后续扩展空间。
