# 上下文构建、预算与记忆生命周期

这篇文档讲当前项目如何把 system prompt、会话历史、当前用户请求、工具结果、记忆、历史向量召回、代码安全 RAG 和 task runtime events 组合成模型上下文，以及一轮结束后如何更新记忆。

## 这层解决什么问题

模型每轮看到的不是完整数据库，也不是随便拼接的字符串。

当前上下文相关实现主要位于：

- `runtime/context.py`
- `runtime/context_budget.py`
- `runtime/context_history.py`
- `runtime/context_sections.py`
- `runtime/working_memory.py`
- `runtime/pipeline.py`
- `memory/store.py`
- `memory/lifecycle.py`
- `runtime/background_memory.py`
- `memory/processor.py`
- `memory/candidates.py`

它要解决这些问题：

- system prompt 和 instruction files 怎么进入模型。
- 历史会话、当前用户请求、当前 active turn 怎么分开治理。
- 工具调用链如何在裁剪后仍然满足 provider 协议。
- memory、历史向量召回和代码安全 RAG 怎么注入上下文。
- working memory 怎么把 coding 断点状态注入上下文。
- task session 的 inbox / background results 怎么进入上下文。
- 上下文过长时先按 section 预算，再在模型调用前做 token gate。
- 一轮结束后如何沉淀显式记忆、候选记忆、历史归档和向量历史。

## ContextBuilder 的输出

`ContextBuilder.build()` 返回：

```python
@dataclass
class ContextBundle:
    messages: list[dict]
    report: ContextBuildReport | None = None
```

它返回的是 chat messages，而不是一个大字符串。`report` 是本轮上下文构造的结构化解释，用于 trace。

`ContextBuilder` 的实际装配顺序是：

```text
system message
budgeted conversation history
optional context frame user message
budgeted active turn
```

注意：`tool_catalog` 不在 `ContextBuilder` 内部插入，而是由 `runtime/pipeline.py` 在上下文构建之后插入到 active turn 之前。最终发给 provider 的顺序会变成：

```text
system message
budgeted conversation history
optional context frame user message
tool_catalog user message
budgeted active turn
```

这样工具目录不会混入历史裁剪逻辑，但也意味着它目前不是 `ContextBuildReport` 的独立 section。

## active turn 边界

`Pipeline` 在每个用户 turn 开始时记录：

```python
active_turn_start_index = _last_user_message_index(session.messages)
```

`ContextBuilder._split_active_turn()` 会据此把 `session.messages` 分成：

- `conversation_history`：active turn 之前的历史。
- `active_turn`：当前用户请求之后发生的消息，包括 assistant tool_call 和对应 tool result。
- `current_request`：active turn 内第一条 user message。

这个设计是为了解决一个关键 bug：如果工具结果很长，不能在下一步构造上下文时把最近的 assistant tool_call 或 tool result 裁掉，否则 provider 会报：

```text
An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'
```

因此 active turn 的预算策略默认是 `latest_tool_call`，目标是：

- 当前用户请求必须完整保留。
- 最近一次 assistant tool_call 必须保留。
- 与最近 tool_call 对应的 tool result 必须保留。
- 更早的工具结果可以压缩成摘要。

具体实现在 `runtime/context_history.py` 的 `budget_active_turn()`。

## logical sections vs chat messages

当前系统采用“逻辑层细，传输层简”的设计。

逻辑 section 包括：

- `system_profile`
- `mode_instructions`
- `project_instructions`
- `runtime_guidance`
- `system_prompt`
- `conversation_history`
- `current_request`
- `active_turn`
- `memory`
- `working_memory`
- `retrieved_history`
- `security_knowledge`
- `task_runtime_events`
- `context_frame`

传输给 provider 的 messages 则更少：

```python
messages = [
    {"role": "system", "content": system_prompt},
    *budgeted_history.rendered_messages,
    {"role": "user", "content": context_frame},  # optional
    {"role": "user", "content": tool_catalog},   # inserted by Pipeline, optional
    *budgeted_active_turn.rendered_messages,
]
```

这样 runtime 内部可以精细统计、预算和 trace，但 provider 侧仍然看到标准 chat messages。

## ContextBuildReport

`ContextBuildReport` 会记录每个 section 的：

- `raw_chars`
- `rendered_chars`
- `budget_chars`
- `truncated`
- `metadata`

如果某个 section 被裁剪，`reductions` 会记录：

```json
{
  "section": "active_turn",
  "reason": "section_budget",
  "before_chars": 18000,
  "after_chars": 7600,
  "budget_chars": 8000,
  "strategy": "latest_tool_call"
}
```

这份 report 会写进 trace 的 `context.build.completed` 事件，方便之后判断“模型这一步到底看到了什么”。

## section budget

section budget 由 `runtime/context_budget.py` 的 `ContextBudgeter` 负责，默认开启：

```text
CONTEXT_ENABLE_SECTION_BUDGET=1
CONTEXT_BUDGET_CHARS=24000
```

默认规则包括：

- `mode_instructions`：head，默认 3000 chars。
- `project_instructions`：head，默认 3000 chars。
- `memory`：head_tail，默认 2000 chars。
- `working_memory`：head_tail，默认 4000 chars。
- `retrieved_history`：head_tail，默认 2500 chars。
- `security_knowledge`：head_tail，默认 3000 chars。
- `task_runtime_events`：tail，默认 1500 chars。
- `conversation_history`：summary_middle，默认 16000 chars。
- `active_turn`：latest_tool_call，默认 8000 chars。

其中 `conversation_history` 和 `active_turn` 不是纯文本 section，而是 chat message section，所以它们由 `runtime/context_history.py` 单独处理。

## conversation history 裁剪

`budget_conversation_history()` 默认使用 `summary_middle` 策略：

- 保留开头若干 turn。
- 保留末尾若干 turn。
- 中间 turn 汇总成一条 synthetic summary message。

默认环境变量：

```text
CONTEXT_HISTORY_KEEP_HEAD_TURNS=3
CONTEXT_HISTORY_KEEP_TAIL_TURNS=6
CONTEXT_HISTORY_SUMMARY_MAX_CHARS=3000
```

它不是简单删除最近消息，而是按 turn 分组处理，尽量保持 user / assistant / tool messages 的语义组合。

## active turn 裁剪

`budget_active_turn()` 会优先压缩旧工具结果，然后再考虑裁剪。

默认保留最近若干工具结果：

```text
CONTEXT_ACTIVE_TURN_KEEP_RECENT_RESULTS=5
```

并对这些工具结果更保守：

```text
CONTEXT_ACTIVE_TURN_PRESERVE_TOOLS=read_file,git_diff,git_status,git_log
```

代码里的默认值还包括：

```text
list_files,rg,code_outline,repo_map
```

这意味着文件读取、搜索、repo map、outline、diff、git 状态这类对 coding agent 继续推理很关键的结果，会比普通长输出更优先保留。

## token gate

section budget 使用字符数治理，但真正的模型限制是 token。

`runtime/reasoning_loop.py` 在模型调用前会执行 provider-aware token estimate。如果预计 token 超过阈值，会触发 emergency trim，并写 trace：

```text
context_emergency_trim
```

所以当前上下文治理有两层：

1. `ContextBuilder` 阶段按 section 预算治理。
2. `ReasoningLoop` 阶段按模型 token 上限做最后门禁。

## system prompt 和 instruction files

system prompt 由三部分组成：

```text
profile.system_prompt
instruction_block
runtime_guidance
```

instruction 文件按 `profile.tool_mode` 选择：

- bot 模式：`.agent/assistant.md`
- coding 模式：`.agent/coding.md` 和 `AGENTS.md`

instruction 文件会被包成：

```text
<instructions section="mode_instructions" sources=".agent/coding.md">
...
</instructions>
```

`ContextBuilder` 对 instruction 文件做 mtime cache，避免每一步重复读盘。

runtime guidance 来自 `ContextBuilder._guidance_registry`，目前包括：

- 需要过去偏好或项目约定时使用 `recall_memory`。
- 用户表达持久偏好或重要事实时使用 `memorize`。
- deferred tools 需要用 `tool_search` 查找或解锁。
- 自动安全 RAG 每个用户 turn 只注入一次；后续需要本地安全知识时用 `security_rag_search`。
- search-like tools 是有限机会，要批量查询并尽量一次拿足证据。

插件也可以通过 `ContextBuilder.register_guidance()` 增加 runtime guidance。

## memory block

如果配置了 memory store，`ContextBuilder` 会先按 session scope 获取 store：

```python
if hasattr(store, "for_session"):
    store = store.for_session(session)
```

然后构造 memory block。当前不是无脑读取全部 memory，而是优先使用：

```python
store.recall(current_request)
```

也就是说，用户有当前请求时，memory block 更偏向“相关记忆片段”，而不是把 `MEMORY.md`、`HISTORY.md`、`PENDING.json` 全量塞进上下文。

如果没有 current request，才会退回到 prompt memory。

## working memory block

working memory 由 `runtime/working_memory.py` 管理，存储在 session metadata：

```text
session.metadata["working_memory"]
```

`ContextBuilder._build_working_memory_block()` 只在这些条件满足时注入：

- `WORKING_MEMORY_RESUME_ENABLED=1`。
- 当前 `profile.tool_mode == "coding"`。
- session 中存在未完成的 working memory。

渲染形式是：

```xml
<working-memory task_id="..." status="...">
...
</working-memory>

<working-memory-instruction critical="true">
...
</working-memory-instruction>
```

它表达的是“已完成哪些线索、待继续哪些线索、最近停止原因是什么”，用于断点式续做提示。它不是精确的 step replay。

## retrieved history

历史会话向量库由 `memory/vector_runtime.py` 构造，通常使用 Qdrant。

`ContextBuilder` 会用当前请求和 active turn 摘要做查询，召回同一 scope 下相似的历史 turn，并渲染成：

```text
<retrieved_history>
...
</retrieved_history>
```

scope 由 `history_vector_scope_for_session()` 决定，常见形态是：

- `user:<user_id>`
- `task:<task_id>`

本地 Markdown 记忆仍然存在；Qdrant 只用于完整历史会话 turn 的向量召回。

## security knowledge

代码安全 RAG 是另一套 collection，不和历史会话向量库混在一起。

如果 `SECURITY_RAG_AUTO_CONTEXT_ENABLED=1`，`ContextBuilder` 会在当前用户请求进入模型前调用安全检索路由：

```python
security_retrieval_router.route(current_request)
```

命中后从 `security_knowledge_index` 搜索本地安全知识库，并把结果注入：

```text
<security_knowledge>
...
</security_knowledge>
```

`Pipeline` 会保证自动安全 RAG 每个用户 turn 只注入一次。后续 reasoning step 如果模型还需要安全知识，应调用 `security_rag_search` 工具，而不是每步自动重复检索。

## context frame 优先级

context frame 由多个可选 block 拼成，顺序是：

1. `security_knowledge`
2. `working_memory`
3. `task_runtime_events`
4. `retrieved_history`
5. `memory`

每段前面会有 `context-priority` 注释，方便之后排查模型到底看到哪些辅助上下文。

## task runtime events

task session + coding profile 下，`Pipeline` 会把这些内容传给 `ContextBuilder`：

- teammate inbox
- background results

`ContextBuilder` 渲染为：

```text
<task_runtime_events>
...
</task_runtime_events>
```

这个 section 默认用 tail 策略，因为后台结果和队友消息通常越新的越重要。

## context sanitize

`ReasoningLoop` 在发给 provider 前会做消息清洗：

```python
context_messages, dropped_messages = _sanitize_context_messages(context.messages)
```

如果有非法或空消息被丢弃，会写 trace：

```text
context.sanitized
```

这层主要处理 provider 协议兼容问题，不负责上下文预算。

## 记忆生命周期

一轮结束后，`memory/lifecycle.py` 的 `MemoryLifecycle` 会处理派生记忆。

主要动作包括：

- 检查用户是否显式要求记忆。
- 使用 summarizer 生成 assistant reply 摘要。
- 追加 `HISTORY.md`。
- 更新 `RECENT_CONTEXT.md`。
- 将被挤出的 recent context 归档到 archive store。
- 将当前 session turn 写入历史向量库。
- 将本地 memory files 写入历史向量库。
- 运行候选记忆处理装置。
- 对满足条件的候选记忆调用 LLM 提取稳定记忆并写入 `MEMORY.md`。

对应 trace 事件包括：

- `memory.lifecycle.scheduled`
- `memory.lifecycle.started`
- `memory.explicit.detected`
- `memory.history.updated`
- `memory.recent_context.updated`
- `memory.archive.updated`
- `memory.vector.turn_indexed`
- `memory.vector.files_indexed`
- `memory.candidate.processed`
- `memory.candidate.promoted`
- `memory.lifecycle.completed`
- `memory.lifecycle.failed`

默认运行时还会把 `MemoryLifecycle` 包成 `runtime/background_memory.py` 的 `BackgroundMemoryLifecycle`：

```text
MEMORY_LIFECYCLE_BACKGROUND=1
MEMORY_LIFECYCLE_BACKGROUND_WORKERS=1
```

这种模式下，`Pipeline._after_turn()` 不直接执行 `after_turn()`，而是调用 `enqueue_after_turn(session, run_state, trace_store)`。后台任务会：

- deepcopy 当前 session 快照，避免后续消息继续变化影响本次处理。
- 在后台线程里调用真实 `MemoryLifecycle.after_turn()`。
- 把 lifecycle result 中的 `trace_events` 转写回当前 run 的 `trace.jsonl`。
- 写 `memory.lifecycle.completed` 或 `memory.lifecycle.failed`。
- 尝试刷新 `trace_summary.json` / `trace_summary.md`。

因此 memory lifecycle 是 turn 后处理，但默认不阻塞用户可见回复；同一个 run 的 memory 摘要可能在主回复完成后才补齐。

## 候选记忆

候选记忆不是只靠关键词匹配。

当前候选处理路径是：

1. `MemoryProcessingDevice` 拿当前用户描述查询历史向量库。
2. 如果相似历史命中数量达到阈值，说明这类信息反复出现。
3. 将本次描述 upsert 到候选记忆库。
4. 候选多次触发后，提高 confidence 和 evidence_count。
5. 满足晋升条件后，交给 LLM 提炼稳定记忆。
6. 写入本地 Markdown 记忆，并把候选标记为 promoted。

候选存储由 `memory/candidates.py` 负责：

- 主存储是 `PENDING.json`。
- 文件中会标明 `backend: "json"`，并保留 candidate id、confidence、evidence_count、source_refs、status 和 metadata，方便人工查看。

## 当前边界

当前上下文系统已经支持 section budget、active turn 保护、向量历史召回、自动安全 RAG 和 token gate，但仍有边界：

- conversation summary 是规则式摘要，不等同于 LLM 长期记忆压缩。
- token estimator 是估算，不是 provider 官方 tokenizer 的逐模型精确计数。
- 自动安全 RAG 只做 turn 开头的一次注入，后续依赖工具调用。
- Qdrant 不替代本地 Markdown 记忆；稳定记忆仍以本地文件为主。
- memory lifecycle 是 turn 后处理，不会在同一轮模型调用中立即改变当前 prompt；默认后台执行，不是持久化队列。
- section budget 是逐 section 裁剪，不是完整全局 allocator；最终仍由 token gate 做最后兜底。
- `tool_catalog` 目前由 `Pipeline` 插入，不在 `ContextBuildReport` 中作为独立 section 统计。

## 总结

当前上下文系统的核心已经从“压缩整段 session messages”变成“按语义 section 治理上下文”。

`ContextBuilder` 负责构造和解释上下文，`ContextBudgeter` 和 `context_history` 负责预算与 active turn 保护，`working_memory` 提供 coding 断点状态，`ReasoningLoop` 做模型调用前 token gate，`MemoryLifecycle` 在 turn 结束后沉淀记忆。这个边界让 trace 能解释每一步模型看到的内容，也避免工具调用链在裁剪后破坏 provider 协议。
