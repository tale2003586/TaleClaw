# 消息入口、会话与身份边界

这篇文档讲清楚一条外部消息进入系统以后，怎么被映射成内部会话和用户身份。

## 这层解决什么问题

当前项目支持多个入口。不同入口的消息形态不一样：

- CLI 是本地输入。
- Web 有用户登录态和 web session。
- Telegram 有 chat/user id。
- 飞书有 open id、chat id 和审批身份。

runtime 不应该直接关心这些入口细节，所以入口层会把外部事件统一成 `InboundMessage`，再交给 `MessageBus`。

## InboundMessage 的含义

核心定义在 `bus/events.py`：

```python
@dataclass
class InboundMessage:
    channel: str
    chat_id: str
    sender: str
    content: str
    timestamp: datetime = field(default_factory=datetime.now)
    media: list[str] = field(default_factory=_empty_media)
    metadata: dict[str, Any] = field(default_factory=_empty_metadata)
```

这里最关键的是：

- `channel`：消息来自哪个入口，比如 `web`、`telegram`、`feishu`。
- `chat_id`：入口侧的会话标识。
- `sender`：入口侧发送者。
- `content`：用户文本。
- `media`：附件路径或媒体引用。
- `metadata`：用户身份、角色、workspace 等额外信息。

`chat_id` 不是数据库里的 session id。它是入口侧的对话 id。内部 session 由 `channel` 和 `chat_id` 组合生成。

## session_key 怎么来

`AgentLoop.run_once()` 中会使用：

```python
session = self.sessions.get_or_create(inbound.session_key)
```

也就是说，真正拿 session 的 key 来自 inbound 自身的 `session_key` 属性。当前实现是一个精确属性：

```python
return f"{self.channel}:{self.chat_id}"
```

因此内部 session key 形如：

```text
web:<chat_id>
telegram:<chat_id>
feishu:<chat_id>
```

这样不同入口即使有相同 chat id，也不会撞到同一个内部会话。

Web 入口还会额外把用户 id 编进 chat id：

```text
web:<user_id>:<chat_id>
```

`web/server.py` 的 `web_chat_id()` / `web_session_id()` 会先规范化 user id 和 chat id，再形成这个 session id。这样同一个浏览器会话名 `default` 在 `alice` 和 `bob` 下会成为不同内部 session。

## 身份怎么进入 session

`AgentLoop._apply_inbound_identity()` 会从 `inbound.metadata` 里读取：

- `user_id`
- `user_role`

如果 session 里已经有 `user_id`，而 inbound 又带了另一个不同的 `user_id`，系统会直接抛错：

```python
if inbound_user_id is not None and session_user_id is not None and inbound_user_id != session_user_id:
    raise ValueError("Inbound user identity does not match the existing session.")
```

这个检查的目标是防止同一个内部 session 被不同用户身份复用。

如果身份一致，或者 session 里还没有身份，runtime 会把 `user_id` 和 `user_role` 写入 session metadata。

## user_role 的作用

`user_role` 会影响工具可见性和模式权限。

例如 `ToolSpec.enabled_for()` 会检查：

```python
if self.admin_only and session is not None:
    return metadata.get("user_role", "admin") == "admin"
```

也就是说，admin-only 工具只有 admin session 可以看见或执行。

模式路由也使用同一个角色边界。`ExecutionPlanner.coding_allowed()` 要求 `metadata.user_role == "admin"`；普通用户执行 `/coding` 会被保持在 bot 模式，hybrid 下识别到 coding 候选也会降级为普通聊天。

多用户隔离也依赖这个边界。测试里覆盖了普通用户不能进入 coding 或看见 admin-only 工具的情况。

## session 里存什么

session 至少承担这些职责：

- 当前会话的消息历史。
- 当前模式，例如 bot、coding、hybrid。
- 用户身份和角色。
- 当前 run id，例如 `active_run_id`、`last_run_id`。
- coding task 绑定的 workspace metadata。
- 工具解锁状态，例如本 turn 里通过 `tool_search` 解锁了什么。
- coding working memory，例如 `working_memory` 和 `working_memory_resume_requested`。

session 是运行时连接上下文、工具、记忆、trace 的中心状态之一。

Web 入口的 turn 互斥也按内部 session key 加锁，而不是使用全局进程级锁。这样同一个 session 内仍然保持消息顺序，不同用户或不同会话不会因为某个长任务在入口层被统一串行化。

## 当前 session 类型

当前代码没有为每类会话定义不同 class，而是复用 `Session`，再通过 `id`、`current_mode` 和 `metadata.kind` 区分：

| 类型 | id 形态 | current_mode | metadata.kind | 主要用途 |
| --- | --- | --- | --- | --- |
| 父级用户 session | `web:<...>` / `cli:<...>` / `telegram:<...>` | `hybrid` / `bot` / `coding` | 通常为空 | 用户可见主对话、身份、last route、workspace、working memory |
| coding task session | `task:coding-<id>` | `coding` | `task_session` | coding 中间推理、工具结果、task-local memory、workspace diff |
| subagent session | `subtask:<agent_type>:<id>` | `coding` | `subagent` | 短生命周期局部事实抽取，结果通过 trace 和 `SubagentResult` 回传 |
| teammate session | `teammate:<name>` | `teammate` | `teammate` | 持久协作角色，通过 team bus 接收任务 |

更细的 profile、instruction md 和 working memory 边界见 [11-会话类型、Profile 与工作记忆边界](11-会话类型、Profile与工作记忆边界.md)。

## 用户数据边界

用户级文件和记忆边界由 `user_scope.py` 统一解析。

带有显式 `user_id` 的 session 会使用：

```text
.users/<user_id>/memory/
.users/<user_id>/storage/
```

如果 session 没有显式 `user_id`，为了兼容旧本地路径，会回退到：

```text
memory/
storage/
```

这影响三类能力：

- `ScopedMemoryStore.for_session()` 会把长期记忆解析到当前用户的 memory root。
- bot/coding 的 storage 工具会把上传、生成报告和发布 artifact 放到当前用户的 storage root。
- Web 的文件列表、预览、下载、上传、重命名、删除也只允许访问当前登录用户的 storage root。

Web 删除会话也走同样边界。`DELETE /api/session` 只能删除当前用户拥有的 `web:<user_id>:<chat_id>` session，不能删除 `task:*` 或其他用户的 Web session。

## SessionManager 和 SessionStore

当前会话内存层在 `sessions/session.py`：

- `SessionManager` 使用 `OrderedDict` 做一个简单 LRU 缓存。
- 默认最多保留 128 个活跃 session 对象。
- `get_or_create()` 会先查内存，再从 `SessionStore` 加载。
- `cleanup_expired_sessions(max_age_days=...)` 可以按 `updated_at` 清理过期 session。

落盘层在 `sessions/session_store.py`。它会写两张表：

- `sessions`：session 元信息、当前 mode、metadata。
- `messages`：按 `session_id + seq` 存储消息 JSON。

保存时不是每次删除重写整段消息历史。`save_session()` 会读取已有 `seq/message_json`，找到第一条变化的消息，然后只删除并重写变化后的尾部。`last_message_insert_count` 用于测试和观测这次保存实际插入了多少条消息。

数据库连接由 `runtime/db.py` 统一处理。当前系统只支持 PostgreSQL：

- `SESSION_DATABASE_URL` 可以单独指定会话数据库。
- 如果没有配置 `SESSION_DATABASE_URL`，会尝试复用 `DATABASE_URL`。
- 如果两者都没有配置，`SessionStore` 会直接报错，避免隐式创建本地关系型数据库文件。
- PostgreSQL 连接由 psycopg 管理，返回 dict-like rows，便于 store 层统一读写。

## 出站消息怎么发回入口

`AgentLoop` 完成一轮后会调用：

```python
await self.bus.publish_outbound(OutboundMessage(
    channel=inbound.channel,
    chat_id=inbound.chat_id,
    content=reply,
))
```

这里保留了原始 `channel` 和 `chat_id`，入口 worker 可以根据它把回复发回 Web、Telegram 或飞书。

## AppRuntime.start() 做什么

`runtime/app_runtime.py` 的 `start()` 会创建一个后台 task：

```python
self._dispatch_task = asyncio.create_task(
    self.bus.dispatch_outbound(),
    name="outbound_dispatch",
)
```

它的作用是持续消费 outbound 队列，把 runtime 产生的回复交给对应入口层。这样 `run_once()` 只需要 publish outbound，不需要直接知道外部平台怎么发送消息。

## 当前边界

这层已经有多入口统一消息和用户身份校验，但它不是完整 IAM 系统。

当前没有实现：

- 细粒度权限策略语言。
- 会话级 token refresh。
- 多租户资源配额。
- 完整审计审批流。

现在的核心边界是：入口把身份放入 metadata，`AgentLoop` 校验并写入 session，工具和 memory 再基于 session metadata 做隔离。

会话数据库保存的是会话状态，不是完整审计证据。完整 run 证据仍以 `.runs/<run_id>/` 下的 trace/report/metrics 工件为准。

## 总结

当前消息入口设计的关键是把外部平台差异收敛成 `InboundMessage` 和 `OutboundMessage`。

`channel + chat_id` 决定会话边界，`metadata.user_id/user_role` 决定用户身份和权限边界。后面的模式路由、工具可见性、记忆隔离、workspace 绑定，都建立在这层 session metadata 之上。
