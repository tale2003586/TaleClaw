# 新服务器 `.env` 配置手册 Spec

## 背景

仓库已有完整的首尔服务器部署文档，但 `.env` 配置内容夹在安装 Docker、Nginx、HTTPS、数据库维护等流程中。新服务器首次部署时，需要一份更短、更聚焦的手册，说明应该从 `.env.example` 复制什么、必须修改什么、哪些功能默认关闭，以及怎样在不泄露密钥的前提下验证配置。

## 目标

- 提供一份面向新服务器首次部署的独立 `.env` 修改手册。
- 给出可直接照做的最小生产配置，并解释每一组关键变量的作用。
- 覆盖当前 TaskState、动态 Prompt 预算和 Artifact 外置的新配置。
- 提供修改前备份、权限设置、配置校验、容器重启和故障排查步骤。

## 功能需求

- F1: 手册适用于 Ubuntu 22.04 / 24.04 上通过 Docker Compose 部署、代码位于 `/opt/taleclaw` 的默认场景，并说明其他路径需要自行替换。
- F2: 手册必须从复制 `.env.example`、设置 `600` 权限和选择编辑器开始，不要求读者直接从零创建 `.env`。
- F3: 手册必须给出模型 Provider、模型路由、PostgreSQL、Web 登录、容器内工作区和新上下文架构的最小生产配置模板。
- F4: 手册必须明确区分“必须修改”“建议保持默认”“按需启用”三类配置。
- F5: 数据库章节必须说明容器内 `postgres:5432` 与宿主机 `127.0.0.1:55432` 的区别，并提醒特殊字符需要 URL 编码。
- F6: 安全章节必须禁止提交或直接输出真实 `.env`，建议使用强随机密码、关闭匿名访问和注册，并在 HTTPS 启用后设置安全 Cookie。
- F7: 新上下文章节必须使用当前 TaskState、语义压缩、Artifact 外置和动态 Prompt 预算配置，不再指导用户调整已被忽略的旧固定压缩阈值。
- F8: 验证章节必须包含 Compose 插值检查、容器实际环境检查、服务重启、状态/日志检查和数据库连通性检查，同时避免在命令输出中暴露 API Key、密码或完整 DSN。
- F9: 手册必须提供常见错误排查：数据库地址错误、数据库密码与已有数据卷不一致、模型地址缺少 `/v1` 或 wire API 不匹配、宿主机绝对路径误写成容器路径、修改后未重建或重启容器。

## 非功能需求

- N1: 手册使用中文，命令和配置块可直接复制，危险操作前给出醒目说明。
- N2: 示例只能使用占位凭据，不包含当前机器或真实服务器的秘密信息。
- N3: 内容与当前 `docker-compose.yml`、`.env.example`、`config.py` 的变量名和默认行为保持一致。
- N4: 手册独立可读，但链接到完整服务器部署文档，避免重复 Docker、Nginx 和证书安装细节。

## 不做的事

- 不覆盖 Docker、Nginx、域名、HTTPS 证书的完整安装过程。
- 不修改真实 `.env`、服务器状态、数据库或容器。
- 不为 Telegram、飞书、Qdrant/RAG 给出完整部署，只列为按需扩展入口。
- 不在本任务中修改 `.env.example`；其同步与精简仍由单独任务处理。

## 验收标准

- AC1: 新手从空白新服务器代码目录出发，能按手册创建权限为 `600` 的 `.env` 并填写最小配置。
- AC2: 配置模板包含当前默认部署必需的 Provider、数据库、Web、安全、工作区和上下文配置，不包含真实密钥。
- AC3: 手册中的变量名可在当前代码、Compose 或 `.env.example` 中找到；所有给出的默认值与当前实现一致。
- AC4: 验证命令不会打印 API Key、登录密码或完整数据库 DSN，并能发现缺失值、Compose 解析错误和服务启动失败。
- AC5: 至少覆盖五类新服务器常见配置错误，并给出可执行的修复方向。
- AC6: 文档明确提示 `.env` 不应提交 Git，修改后需重建或重启对应服务。
