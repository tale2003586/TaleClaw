## 一、记忆系统

### 1.1 `MemoryStore.recall()` 是空壳

**严重度**：🔴 高
**文件**：`memory/store.py:176-181`

```python
def recall(self, query: str | None = None) -> str:
    text = self.read_all()
    if not query:
        return text
    # 第一版先不做检索，直接返回全文。
    return text
```

`recall_memory` 工具无视查询内容，永远返回全部记忆。随着记忆增长（PENDING.md / MEMORY.md / SELF.md / NOW.md / HISTORY.md），这会变成一个撑爆上下文的完整 dump。没有向量搜索、没有关键词过滤、没有分区选择。

**修复**：将 `recall_memory` 路由到 `history_vector_index`，scope 从 session 派生。记忆文件应在 `after_turn` 中被 embed 并索引，`recall` 应该做向量搜索而非文件原始读取。

### 1.2 候选记忆流水线默认不工作

**严重度**：🔴 高
**文件**：`memory/processor.py:57-73`、`memory/vector_runtime.py:11-16`

`MemoryProcessingDevice.process_user_description()` 依赖 `history_vector_index`，而 `history_vector_index` 需要 `HISTORY_VECTOR_ENABLED=true`（默认 `False`）。开关关闭时整条候选记忆流水线返回空结果：
- 不会从用户消息中自动提取候选记忆
- 不会跨轮次检测重复模式
- 不会从候选升级（promote）为确认记忆
- `_candidate_memory_enabled()` 虽然返回 `True`，但流水线是空操作

**修复**：将 `HISTORY_VECTOR_ENABLED` 默认改为 `True`，或者在向量索引关闭时实现轻量级关键词回退。

### 1.3 `CandidateMemoryStore` 每次写入都是 O(n)

**严重度**：🟡 中
**文件**：`memory/candidates.py:54-122`

每次 `upsert()` 读全量 JSON → 反序列化全部候选 → 改一条 → 序列化全部 → 写全量文件。几百条候选时 I/O 很重。没有增量追加，没有索引。

**修复**：用 SQLite（像 `MemoryArchiveStore` 那样）替代 JSON 文件，或者用脏标记做批量写入。

### 1.4 `_render_messages_for_embedding()` 嵌入了 JSON 噪音

**严重度**：🟡 中
**文件**：`memory/lifecycle.py:228-240`

```python
def _render_messages_for_embedding(self, messages):
    for message in messages:
        parts.append(f"{role}: {_compact_json_or_text(content)}")
```

当 `content` 不是字符串时，`_compact_json_or_text` 调用 `json.dumps()`，把结构化 JSON 打入 embedding 文本。语法字符稀释了语义信号。

**修复**：只提取文本字段，跳过 JSON 结构符。

### 1.5 记忆去重是纯字符串匹配

**严重度**：🟡 中
**文件**：`memory/dedup.py`

`normalize_memory_text()` 去标点 + 小写后做精确匹配。"使用 pytest 做测试"和"用 pytest 运行测试"不会被识别为近似重复（归一化后 token 集合不同）。

**修复**：用 embedding 余弦相似度（阈值 ≥0.92）做第二道近似去重检查。

### 1.6 `_MEMORY_KEYWORDS` 硬编码

**严重度**：🟢 低
**文件**：`memory/candidates.py:208-222`

关键词集合 `{"pytest", "测试", "代码风格", ...}` 硬编码且包含领域特定词（"同人文"、"人物细节"），疑似从某个具体场景直接复制。不可配置。

**修复**：改为 env 可配置列表或从配置文件加载。

### 1.7 `MemoryArchiveStore` 与 `SessionStore` 共用数据库

**严重度**：🟢 低
**文件**：`memory/archive_store.py:34-37`

两者共用默认的 `sessions.db`。不同关注点（会话状态 vs 已归档记忆）共享一个数据库文件造成不必要的耦合，备份和恢复更困难。

**修复**：给 `MemoryArchiveStore` 独立的默认数据库路径。

### 1.8 `HistorySummarizer.__init__` 的 dead code

**严重度**：🟢 低
**文件**：`memory/history_summary.py:21-26`

```python
if self.runner is None and provider is not None and model:
    self.runner = ModelTaskRunner(provider=provider, model=model, ...)
```

但在 `bootstrap.py` 中，`HistorySummarizer` 以 `runner=model_task_runner` 方式构造。`provider` 和 `model` 参数永不被使用——死代码路径。

## 二、会话管理

### 2.1 每次保存时全量删插

**严重度**：🔴 高
**文件**：`sessions/session_store.py:113-135`

```python
self._conn.execute(sql(self.config, "DELETE FROM messages WHERE session_id = ?"), (session.id,))
execute_many(self._conn, self.config, "INSERT INTO messages ...", [...])
```

每次 `save_session()` 删掉该 session 的全部消息然后重插。500 条消息就是 501 条 SQL，每个 turn 执行一次。O(n) 写放大。

**修复**：追踪 `last_saved_seq`，只 INSERT 上次保存之后的新消息。

### 2.2 `SessionManager.get_or_create()` 内存泄漏

**严重度**：🟡 中
**文件**：`sessions/session.py:52-67`

Session 在 `self._sessions` dict 中永久缓存。无 eviction，无 TTL。长期运行的服务器上，多用户/多 session 会无限增长。

**修复**：加 LRU 驱逐策略。

### 2.4 无会话过期清理

**严重度**：🟢 低
**文件**：`sessions/session.py`

Session 有 `created_at` 和 `updated_at`，但没有任何代码读取它们来判断过期。数据库和磁盘存储无限增长。

**修复**：添加后台线程或 cron 任务，删除超过 N 天不活跃的 session。

## 三、工具系统

### 3.1 `ToolPolicy.requires_approval()` 永远返回 `False`

**严重度**：🟡 中
**文件**：`tools/policy.py:166-175`

方法签名完整（接受 tool_name、args、session、mode、run_context），但永远返回 `False`。审批工作流（危险工具 → 询问用户 → 执行）完全是 stub。

**修复**：要么实现审批流程，要么删除 stub 避免错误预期。

### 3.2 `ToolLoopGuardHook` 精确指纹匹配太宽松

**严重度**：🟡 中
**文件**：`tools/hooks.py:99-112`

`_fingerprint()` 对 `{tool_name, arguments}` 做哈希。模型调用 `bash("pytest test_a.py -x")` 再调用 `bash("pytest test_b.py -x")` 产生不同指纹——但模型可能在测试-修复循环中连续调用 `bash` 10 次（参数微调），此 guard 检测不到。

**修复**：加一道仅按工具名的重复计数器：同一工具在窗口内调用 >5 次（不管参数），触发 guard。

### 3.3 `ShellSafetyHook` 拦截列表太窄

**严重度**：🟡 中
**文件**：`tools/hooks.py:21-23`

```python
dangerous = ["rm -rf /", "sudo", "shutdown", "reboot", "> /dev/"]
```

缺失：`rm -rf .`、`rm -rf *`、`mkfs`、`dd if=`、`chmod 777`、fork bomb `:(){ :|:& };:`、`/dev/sda` 等。黑名单方式从根本上不完全。

**修复**：考虑沙盒方式（Docker 容器、chroot 或受限用户）而非模式匹配。

### 3.4 `DEFERRED_TOOLS` 包含 `task` 和 `parallel_tasks`

**严重度**：🟢 低
**文件**：`tools/policy.py:66-82`

`task` 工具在 `DEFERRED_TOOLS` 中，不在 `PRELOADED_TOOLS_BY_MODE["coding"]`。lead agent 必须先 `tool_search select:task` 才能 spawn 子 agent——给最重要的工具增加了摩擦。

**修复**：将 `task` 移到 `PRELOADED_TOOLS_BY_MODE["coding"]`。

## 四、模型/Provider 系统

### 4.1 `config.py` 在 import 时产生副作用

**严重度**：🔴 高
**文件**：`config.py:8-43`

`config.py` 在 import 时执行：
- `load_dotenv(override=True)`——可能全局改写环境变量
- 设置 `HTTP_PROXY`/`HTTPS_PROXY`——影响进程中所有 HTTP 客户端
- 构建 `MODEL_POOL`（校验 env var，可能 raise）
- 运行 `health_check_purposes()`（如果启用）——import 时发起 API 调用

任何一点报错都会在 `main()` 之前让进程崩溃。

**修复**：将有副作用的初始化移到 `build_runtime()` 或 `init()` 函数中。`config.py` 只定义常量/默认值。

### 4.2 `MODEL_HEALTHCHECK_RESULTS` 在 import 时执行

**严重度**：🟡 中
**文件**：`config.py:39-43`

`LLM_HEALTHCHECK_ON_STARTUP=true` 时，模块 import 发起阻塞 API 调用。`python -c "import config"` 可能挂好几秒。

**修复**：将 health check 移到 `bootstrap.py`，不在模块级别执行。

### 4.3 `SYSTEM` 提示词在 import 时捕获

**严重度**：🟢 低
**文件**：`config.py:83-87`

```python
SYSTEM = f"""...Skills available: {SKILL_LOADER.get_descriptions()}"""
```

`SKILL_LOADER.get_descriptions()` 只在 import 时调用一次。运行时添加/移除 skill 后，这个字符串过期直到进程重启。

**修复**：改为函数 `def get_system_prompt()`，在 context build 时调用。

### 4.4 `ModelTaskRunner` 无错误处理

**严重度**：🟡 中
**文件**：`models/model_task_runner.py:20-35`

`run()` 调用 `provider.chat()` 没有 try/except。API 失败时异常直接传播到 caller。各 caller（`HistorySummarizer`、`CandidateMemoryExtractor`）各自 try/except——错误处理不一致。

**修复**：在 `ModelTaskRunner.run()` 中统一错误处理，或明确文档要求 caller 自行处理。

### 4.5 `RoutedModelProvider` 流式 Failover 的副作用

**严重度**：🟢 低
**文件**：`models/model_pool.py:391-393`

```python
if stream and emitted:
    raise  # 已经有部分输出给用户看了，不再重试
```

行为是正确的但未文档化。流式调用中途失败且已输出部分文本时，立即 raise 而非尝试 fallback。Caller 可能不预期此行为。

**修复**：写入 docstring。

## 五、路由系统

### 5.1 `IntentClassifier` 是纯关键词匹配

**严重度**：🟡 中
**文件**：`runtime/routing/intent.py`

全部分类靠子串匹配。示例：
- "帮我查找一下文件" 触发 coding intent（因为含 "文件"）
- "这段代码风格怎么样" 触发 coding intent（含 "代码"+"风格"）
- 没有对用户实际意图的语义理解

**修复**：给关键词分类器加 embedding 回退，类似 security RAG router 的两阶段设计。或提前使用 `HybridModeClassifier`（基于 LLM）。

### 5.2 模式切换检测逻辑重复

**严重度**：🟢 低
**文件**：`runtime/routing/intent.py:21-41` vs `runtime/routing/execution_plan.py:27-68`

`IntentClassifier.classify()` 检测 `/coding`、`/chat`、`/hybrid` 命令并设置 `command`。`ExecutionPlanner.plan()` 再次检查 `command`。逻辑分成两个类没有明确理由。

**修复**：统一到 `IntentClassifier`；`ExecutionPlanner` 只做 intent→execution 映射。

## 六、插件系统

### 6.1 `PluginManager.register()` 污染插件对象

**严重度**：🟡 中
**文件**：`plugins/plugin_manager.py:41`

```python
setattr(plugin, "_plugin_manager", self)
```

给插件对象添加私有属性。如果插件是 frozen dataclass 或有 `__slots__`，这直接失败。也是违反封装的。

**修复**：用 `WeakKeyDictionary` 存储反向引用，或把 `PluginManager` 作为参数传给 hook 方法。

### 6.2 插件注册只能加不能删

**严重度**：🟢 低
**文件**：`plugins/plugin_manager.py:33-57`

没有 `unregister()`。如果需要热重加载或禁用插件，没有机制。

**修复**：加 `unregister(plugin_name)` 方法，反向执行注册步骤。

## 七、Web/API 层

### 7.1 `ThreadingHTTPServer` 不适用生产环境

**严重度**：🟡 中
**文件**：`web/server.py`

标准库的 `ThreadingHTTPServer` 已知局限：无连接池、无优雅关闭、无限流、无 TLS、易受 slow-loris 攻击。

**修复**：生产环境使用 uvicorn/FastAPI，或至少反向代理（nginx/caddy）。文档化此限制。

### 7.2 已废弃的 `cgi` 模块

**严重度**：🟢 低
**文件**：`web/server.py:28`

```python
import cgi  # Python 3.11 废弃，3.13 移除
```

`cgi` 模块用于解析 multipart 表单数据。Python 3.13+ 上会彻底失效。

**修复**：替换为 `email.parser` + `urllib.parse`，或使用 `python-multipart` 库。

## 八、错误处理（全局）

### 8.1 大量裸 `except Exception` 用法

**严重度**：🟡 中
**范围**：43 个文件，约 200 处

许多 `except Exception` 块静默吞错：

```python
# memory/processor.py:126-127
except Exception:
    return []

# models/model_pool.py:390
except Exception as exc:
    ...
```

最严重的问题模式：
- `tools/handlers.py`：18 个 `except Exception` 块，很多返回 `f"Error: {e}"`——有用但不一致（有的返回错误字符串，有的返回空 dict，有的 print）
- `coding_runtime/teammate.py:161`：`except Exception as e: print(f"[{name}] Error: {e}")`——teammate 崩溃对 lead 完全不可见

**修复**：采用一致的错误处理模式：log → trace → 返回结构化错误。添加自定义 `AppError` 基类区分预期错误和意外异常。

### 8.2 无结构化日志

**严重度**：🟢 低
**范围**：全局

所有输出都用 `print()`。无日志级别、无时间戳前缀、无结构化格式、无文件轮转。生产环境调试靠 grep stdout。

**修复**：采用 `logging` 模块，stdout + 文件 handler 配置。

## 九、工作区

### 9.1 `safe_workspace_path()` 不检查符号链接

**严重度**：🟡 中
**文件**：`runtime/workspace.py:104-112`

函数拒绝路径中的 `..` 但不先解析符号链接。工作区内指向 `/etc/passwd` 的符号链接会通过检查。

**修复**：先 `resolve()` 再检查包含关系：`target.resolve()` 后 `is_relative_to(root.resolve())`。

### 9.2 `_session=None` 时不报错

**严重度**：🟢 低
**文件**：`runtime/workspace.py:104-112`

`safe_workspace_path(path, session=None)` 回退到 `workspace_root_for_session(None)`，返回 `DEFAULT_CODING_WORKSPACE`。如果有代码路径忘记传 session，它静默拿到默认工作区而不是报错。

**修复**：要求 `session` 参数；为 None 时 raise `ValueError`。

## 十、测试覆盖缺口

**严重度**：🟡 中

39 个测试文件覆盖面不错，但关键路径缺失：

| 缺口 | 风险 |
|------|------|
| 无 `ModelPool` fallback 链测试 | Provider 故障转移可能失效而不被检测 |
| 无 `SessionManager` 并发访问测试 | SQLite 线程问题只在压力下暴露 |
| 无 `PluginManager` 生命周期测试（register→before_turn→after_turn→after_run） | 插件排序 bug 抓不到 |
| 无 `WorkspaceResolver` 边界测试（符号链接、不存在路径） | 路径穿越可能存在 |
| 无 `MemoryLifecycle` 端到端测试（turn→candidate→promotion→recall） | 记忆流水线 bug 只能生产环境发现 |
| 无 `CandidateMemoryStore` 并发写测试 | 多线程下 JSON 文件损坏 |
